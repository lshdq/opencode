# 需求：优化 dev-workflow 流程

## 背景与目标

现有 dev-workflow 在多个阶段重复要求用户确认，并在文档生成后设置独立审核阶段，打断连续开发流程。目标是只保留需求澄清和方案设计两个必要确认点，方案确认后切换到 build 模式并自主执行至完成。

## 功能描述

### 核心功能

- 阶段 1“需求澄清”完成后，必须获得用户明确确认。
- 阶段 2“方案设计”完成后，必须获得用户明确确认。
- question 工具不可用时，阶段 1 和阶段 2 均使用普通对话请求明确确认，不得跳过确认点。
- 阶段 2 通过 `plan_exit` 的内置提问完成唯一一次方案确认，同时退出计划模式并由 build agent 继续执行。
- 使用 `plan_exit` 前必须完成并复核 plan 文件；选择 No 时保持 plan agent、禁止进入阶段 3，并等待用户下一条消息提供调整意见，不依赖运行时是否在拒绝后继续处理。
- 当前已是 build agent 或客户端未注册 `plan_exit` 时，阶段 2 优先使用 question 工具完成唯一一次确认；question 也不可用时使用普通对话请求明确确认；已在 build agent 时确认后直接继续，无法自动切换时按真实阻塞处理。
- 删除原阶段 4“用户审核”。
- 原阶段 5-8 重编号为阶段 4-7。
- 阶段 3-7 自动连续执行，任务分解、测试失败处理和审查问题处理均不再等待用户确认。
- 测试或审查发现问题时，自主修复并重复验证，直至通过或遇到真实阻塞。

### 边界与约束

- 仅修改全局 `dev-workflow` skill，不修改 OpenCode 运行时代码。
- 权限不足、外部环境不可用或需求存在无法自主消解的矛盾时，允许询问用户。
- 保留需求文档、测试用例、独立测试和独立代码审查步骤。

## 输入输出

- 输入：用户提出的代码改动需求及对阶段 1、阶段 2 的确认。
- 输出：七阶段开发流程；支持 `plan_exit` 时阶段 2 确认后自动切换 build，已在 build 时直接继续，其他环境按降级或真实阻塞规则处理；进入 build 后连续执行至完成。

## 非功能需求（性能/安全/兼容性）

- 技能内部的阶段编号、流程摘要和强制规则必须一致。
- 不得残留“每个阶段确认”“任务清单确认”“测试失败后询问”“审查问题后询问”等冲突指令。
- 技能文件仍须符合 OpenCode skill frontmatter 和 Markdown 格式。

## 依赖

- OpenCode `question`、`plan_exit`、`todowrite` 和 `task` 工具。
- `test-workflow` 与 `code-review` skills。
- `plan_exit` 仅在支持该工具的计划模式客户端中用于自动切换。

## 验收标准

- 流程明确为七阶段，且不存在原阶段 4“用户审核”。
- 仅阶段 1 和阶段 2要求用户明确确认。
- 支持 `plan_exit` 时，阶段 2 通过其内置提问同时完成确认与模式切换；已在 build 时确认后直接继续；其他环境按降级或真实阻塞规则处理，且避免重复确认。
- 技能准确处理 `plan_exit` 的 Yes、No、`continue_loop_on_deny` 和确认工具不可用分支。
- 阶段 3-7 明确无需用户确认并连续执行。
- 测试和审查问题能够自主修复、复测和复审。
- 真实阻塞是阶段 2 后唯一允许询问用户的例外。
