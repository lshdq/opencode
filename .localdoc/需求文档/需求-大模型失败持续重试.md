# 需求：大模型失败持续重试

## 背景与目标

当前大模型调用在达到有限重试次数后会结束任务；限额、服务端临时错误或连接异常恢复后，用户需要手动重新提交任务。目标是让可恢复的大模型失败进入持续定时重试，直到成功或用户主动停止任务。

## 功能描述

### 核心功能

- 对限流、账户/服务限额、服务端临时错误、可安全重试的连接失败、流式响应中断等错误持续重试。
- 采用指数退避，单次等待时间最高 5 分钟。
- 尊重服务商返回的 `Retry-After`，但其等待时间不得超过 5 分钟。
- 重试次数不设上限。
- provider 插件不能通过将已判定可重试的错误设置为 `retry: false` 来终止重试，但可以调整等待时间。
- 用户主动停止、Location 关闭和系统取消仍然立即终止执行。

### 边界与约束

- 认证失败、请求参数错误、内容安全拦截、模型不存在、无路由和明确不支持的操作不进入无限重试。
- 传输错误继续遵守 delivery 安全约束，避免对已确认被服务商接受的写请求盲目重复提交。
- 不改变重试事件和现有 UI 状态模型；每次重试仍发布 `session.retry.scheduled`。

## 输入输出

- 输入：大模型调用产生的 `AIError`、provider 返回的重试等待信息、provider retry hook 决策。
- 输出：重试调度事件、等待指定时间后的下一次大模型调用；不可重试错误继续输出现有会话错误。

## 非功能需求（性能/安全/兼容性）

- 退避上限为 5 分钟，避免高频请求加剧服务商限流。
- 保留 `Retry-After` 的服务商节流意图。
- 不重复提交已确认接受的请求，避免重复模型调用或副作用。
- 保持现有插件 hook、会话取消和 Location 生命周期兼容。

## 依赖

- `packages/ai` 的 provider 错误分类与可重试判定。
- `packages/core` 的 SessionRunner retry policy、重试事件和执行生命周期。

## 验收标准

1. 限额、限流、服务端临时错误和可安全重试的连接失败不会因次数耗尽而结束任务。
2. 连续失败时每次等待按指数退避增长，单次等待不超过 5 分钟。
3. 服务商提供的 `Retry-After` 被遵守且不超过 5 分钟。
4. provider hook 将可重试错误改为 `retry: false` 后，任务仍会按策略继续重试。
5. 认证、参数、内容策略和无路由错误仍然失败，不进入无限循环。
6. 用户主动取消和 Location 关闭行为不受影响。
