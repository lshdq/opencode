# 需求：开发任务复杂度模型路由

## 背景与目标

OpenCode 当前开发流程固定由主智能体或 `general` 子智能体处理不同复杂度的任务，无法按任务难度匹配不同模型。目标是在不新增 Router Agent、不修改内置 `plan` 提示词的前提下，由 `dev-workflow` 对阶段 5、6、7 内的每个子任务分别判断复杂度，并委派给对应模型的子智能体。

## 功能描述

### 核心功能

- 新增 `dev-fast`、`dev-standard`、`dev-deep` 三个全局子智能体。
- 三个子智能体的模型和思考深度统一在全局 `opencode.jsonc` 中配置。
- `dev-workflow` 在阶段 5、6、7 对每个待委派子任务单独分级。
- 简单、中等、复杂子任务分别委派给 `dev-fast`、`dev-standard`、`dev-deep`。
- 阶段 6 和阶段 7 继续使用独立会话，分别加载 `test-workflow` 和 `code-review`。

### 边界与约束

- 三个 Agent 的 `mode` 必须为 `subagent`，不能作为默认主智能体。
- 当前 `plan` Agent 必须明确禁止调用三个 Agent，`build` Agent 必须明确允许调用。
- 本次只约束当前内置 `plan`；未来新增主 Agent 时，需要单独配置其调用权限。
- 子智能体不允许继续委派其他子智能体，避免嵌套路由。
- 不增加 Task Router，不修改内置 `plan` Agent 的提示词。
- 不改变七阶段开发流程和阶段 1、2 的确认机制。

## 输入输出

- 输入：阶段 5、6、7 中待执行的开发、测试、审查或修复子任务。
- 输出：复杂度等级、选择的子智能体，以及该子智能体的执行结果。

## 非功能需求（性能/安全/兼容性）

- 简单任务优先低延迟模型，减少不必要的推理成本。
- 高风险、跨模块或高不确定性任务必须使用复杂档模型。
- 权限配置不得破坏现有 `build`、`plan`、`general`、`explore` 行为。
- 全局配置必须通过 OpenCode 严格配置校验。

## 依赖

- OpenCode Agent 文件加载机制。
- `agent.<name>.model`、`agent.<name>.variant` 和 `permission.task` 配置。
- `dev-workflow`、`test-workflow` 和 `code-review` Skills。

## 验收标准

- OpenCode 能识别三个新增子智能体及其配置模型和 variant。
- `build` 的 Task 工具可见并可调用三个新增子智能体。
- `plan` 的 Task 工具不可见且不能调用三个新增子智能体。
- `dev-workflow` 明确定义统一分级标准，并在阶段 5、6、7 对每个子任务分别路由。
- 阶段 6、7 的独立测试和独立审查约束保持有效。
- 配置和 Skill 修改通过解析、模型存在性、权限和内容一致性验证。
