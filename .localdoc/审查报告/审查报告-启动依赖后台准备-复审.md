## 4. 经复核成立的发现

### R-005 [阻塞] 必需 workspace 配置失败被吞掉，待发送消息使用旧配置和旧 auto 权限执行

- **证据**：`packages/tui/src/routes/session/index.tsx:309-322` 捕获 `sync.bootstrap({ fatal: false, signal })` 的异常后继续 hydration，`:334` 将整个 hydration 作为 nonfatal 任务；`packages/tui/src/context/sync.tsx:558-569` 实际会抛出必需 config/providers/agent/command 请求的错误；`packages/tui/src/component/prompt/index.tsx:1013-1040` 等屏障通过后只检查 agent/model 与 workspace 连接状态，不校验它们是否来自当前 workspace。权限实际执行在 `packages/tui/src/context/sync.tsx:203-211`，auto 模式会自动回复权限请求。
- **根因**：将“workspace 已消失、保留只读历史”的降级策略，泛化为“任意必需配置失败都可以沿用旧状态继续”。注释中的 non-interactive 并没有覆盖 workspace 仍 connected 而 `/config` 返回 500 的分支；catch 后 barrier 被视为成功。
- **触发条件**：旧配置成功加载（例如 `auto_approve=true`），目标 workspace 状态为 connected，切换到其会话，在新配置仍加载时提交；新 `/config?workspace=...` 返回 500 或抛网络错误，其余 session hydration 正常。
- **只读真实宿主复核**：本轮在 `packages/tui` 运行 `bun -e`，使用真实 `app.run`、OpenTUI Textarea/Enter、真实上下文；仅 HTTP 边界注入可控响应。新 workspace config 返回 HTTP 500 `workspace config unavailable` 后，观察到：

  ```json
  {
    "sends": [{
      "path": "/session/ses_new/message",
      "body": {"agent":"build","model":{"providerID":"test","modelID":"model"},"parts":[{"type":"text","text":"must not use previous config"}]},
      "mode": "Disable auto-approve permissions"
    }],
    "config": {"auto_approve":true,"username":"OLD"},
    "route": {"name":"session","params":{"sessionID":"ses_new"}}
  }
  ```

  即新配置失败后真实提交链仍发出一次 message，当前配置仍是 OLD，auto 仍开启。没有执行真实模型或实际工具；自动批准后果由活动权限处理代码确认，不冒称已执行危险操作。
- **历史归属**：吞异常的 catch 为 **pre-existing**，本次继续保留并将其纳入新的“必要准备”屏障；新增后台权限配置也沿用同一状态。它是累计实现及修复邻接调用链中仍未满足显式需求的既有缺陷，不能把它当成就绪证明。
- **影响/不修复后果**：违反“认证、模型、工具及配置不能以半初始化状态用于消息执行”；connected 并不证明配置可用，旧 auto 状态可能令新 workspace 的工具请求不经用户确认。
- **建议**：区分不存在/断连 workspace 的只读降级与当前 owner 的必需配置失败；后者必须形成可见的、路由作用域的失败或显式 not-ready 状态，保留草稿且阻止所有后续提交，离开时仍可解除，不能只拒绝当前一次后让重提通过。确保 current workspace 与已应用配置来源相符，不能以清空提示或默认旧模型作为恢复。补持久化回归：connected workspace 的 config/providers/agent/command 分别失败，首次等待和重提均零 message/shell，错误可见，离开后有效新路由仍可发送。

### R-006 [阻塞] workspace 切换部分完成后返回主页，取消释放屏障却保留新 path，导致新目录配旧配置发送

- **证据**：`packages/tui/src/context/project.tsx:38-53` 在自己的 path/project 请求结束后立即写入全局 path；`packages/tui/src/context/sync.tsx:463-489,510-530` 的配置需要等待另一组请求才写入；`packages/tui/src/routes/session/index.tsx:289-290,310-318` 卸载取消 owner；`packages/tui/src/context/preparation.tsx:23-29` 立即移除并完成其 barrier，却不回滚已写入的数据。主页 `packages/tui/src/routes/home/session-destination.tsx:27-28` 直接以 `sync.path.directory` 为默认目标；`component/prompt/move.tsx:166-172` 读取该目录，`component/prompt/index.tsx:1013-1064` 使用旧 agent/model 创建会话。Home 没有为该部分完成的 workspace 补建必要配置屏障。
- **根因**：失效 signal 只能阻止未来写入，不能撤销取消之前已经发生的 path/project/current workspace 写入。屏障所有权解绑解决了 R-004 的卡住，但 path/config/permission 没有作为一致的已就绪状态应用或回退。
- **触发条件**：进入 workspace A 的会话，A 的 `/path` 和 project 请求快速完成，但 A 的 `/config` 仍挂起；此时返回 Home，编辑并提交新草稿。不需要旧请求失败、重复取消或高并发。
- **只读真实宿主复核**：本轮两次诊断（第二次补采请求完整 URL），均保留新 config deferred 未完成，先等待 `api.state.path.directory === "/new-workspace"`，导航 Home 后真实 Enter。第二次实际输出：

  ```json
  {
    "creates": [{"url":"http://test/session?directory=%2Fnew-workspace","body":{"agent":"build","model":{"providerID":"test","id":"model"}}}],
    "sends": [{"url":"http://test/session/ses_created/message","body":{"agent":"build","model":{"providerID":"test","modelID":"model"},"parts":[{"type":"text","text":"new home draft"}]}}],
    "config": {"auto_approve":true,"username":"OLD"},
    "path": {"home":"","state":"","config":"","worktree":"/new-workspace","directory":"/new-workspace"}
  }
  ```

  新 workspace 的配置始终未就绪时，已向其目录创建会话并发送一次消息；前一次诊断也确认 permission mode 仍是 auto。不是仅界面显示路径错误：目录确实出现在 session.create 请求的 query 中。
- **历史归属**：path 先行写入是旧架构行为；本轮新增 owner 取消/屏障解绑允许在配置仍未完成时离开并立即提交，使这条新取消路径暴露了确定的部分状态问题。与 R-005 不同，此处没有错误被吞掉，必须处理取消前已生效的状态。
- **影响/不修复后果**：界面不再卡住，但新的目录/项目与旧模型、agent、命令和 auto 权限组成了错误执行上下文，违反必要配置就绪与恢复/取消一致性要求。
- **建议**：将 workspace 选择/加载中状态与“已完整应用的执行上下文”分离。可选择在全部必要数据就绪后原子应用 path/config/permissions，或取消时恢复已提交的上下文；若 Home 按产品语义保留新目录，则必须建立该目录自己的有效配置准备，而不是继续等待旧 owner 的 IO。修复不得重新引入 R-004 的旧请求无限阻塞。补持久化回归：新 path 已写入、config 挂起后返回 Home，断言不能以新 directory + 旧配置发送；覆盖旧 config 迟到成功/失败及保留 CLI/主动权限选择。
- **现有测试为何未覆盖**：`app-startup.test.tsx:673` 同时挂起旧 path 和 config，旧 path 从未先应用；`:707,785` 导航到另一 Session，由新 Session 主动重新 bootstrap。R-004 的 Home 矩阵挂起的是 session.get/messages，不是已写入 path 后的 config，因此上述全绿与本发现不矛盾。
