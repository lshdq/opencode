### 1.1 R-012专项复核

1. **来源与真实可达性**：`useEvent`保留directory/workspace；`opencode/src/project/instance-store.ts:79-98,126-141`确实发布disposed；`bus/global.ts:14-18`补齐事件ID。`matches`比较workspace及已知directory，不把所有local目录视为同实例。
2. **旧committed事件不抢占C**：`sync.tsx:482-496`仅保留stale，不调用显式候选替换；normal/shell的TC-033断言config请求为local、C，且最终恰好发向C。没有依靠吞AbortError放行。
3. **候选自身失效仍属于同一个外层task**：`:534-563`仅令当前pass失效，重新执行完整只读准备；Session等待的bootstrap Promise身份不变。`:624-650`在发布前检查有效性及删除事实。旧成功/HTTP500/transport rejection不覆盖新结果或制造有效Session失败。
4. **事件去重和新失效**：events集合在候选内去重；同一同步投递批的后续ID均记录，但pass已abort时不再重复启动；后续真正不同ID可以使下一轮再次失效。SDK本身首事件立即flush、后续16ms批处理，不能把跨批通知误判为重复；独立补测已正确区分。
5. **微任务收尾**：`:553-559`在race结果处理前复查pass是否被撤销，成功时同步关闭pending；排除了仅依赖race选中结果、遗漏同一收尾窗口失效的路径。此项为源码调度推演，不声称精确插桩穷举过所有微任务窗口。
6. **dirty fallback和退出**：候选失败不清除其失败；取消后通过队列回查当前候选身份再刷新保留实例；显式新候选安装后旧回调不接管它。removed检查和disposed检查优先。TC-036及独立shutdown补测覆盖取消回退、失败、旧IO未完成及销毁后不再刷新/发送。
7. **provider无参bootstrap**：`:511`复用在途task，不重放auth/dispose或业务请求；TC-038实际走API key确认，断言auth/dispose各一次、config两次。这个正确性结论不包含调用方完成后是否仍有权替换当前窗口；后者有独立问题R-013。

### R-013 [应改] provider认证窗口已关闭，迟到完成仍替换用户新打开的窗口（pre-existing）

- **检查项/结论**：异步调用方生命周期。R-012正确协调bootstrap任务，不会自动撤销原provider回调对当前dialog的访问权限；回调仍可覆盖一个完全不同的新窗口。
- **证据**：`packages/tui/src/component/dialog-provider.tsx:395-415`依次await auth.set、instance.dispose、sync.bootstrap，最后无条件`dialog.replace(() => <DialogModel ... />)`；没有捕获或检查route/dialog signal或组件卸载状态。OAuth对应`:265-283,325-334`也有同类无守卫完成分支。`ui/dialog.tsx:123-125,153-165`虽已推进generation，但只有主动捕获并检查signal的调用方才受保护。`sync.tsx:511`只复用task，不能保护返回后的UI回调。
- **触发条件**：真实Connect provider→API key确认，`instance.dispose`响应尚未完成→Escape关闭认证窗口→打开Sessions→旧dispose及准备正常完成。无需网络失败、路由切换、多个renderer或重复认证。
- **本轮只读宿主证据**：从`packages/tui`用`bun -e`启动真实app.run/OpenTUI，真实Enter/Escape和`provider.connect`、`session.list`命令；仅HTTP和持久化IO边界受控。实际输出：

  ```json
  {"beforeSessions":true,"afterSessions":false,"configs":2,"auths":1}
  ```

  捕获render frame显示新Sessions已经被标题为`Test`的provider模型选择窗口替换。用户没有重新打开provider/model窗口，auth确实只执行一次。诊断没有注入disposed事件，覆盖无参bootstrap自己启动准备的分支；即使走TC-038的共享task，`:415`完成回调也没有额外授权检查，但不将该变体冒称已动态执行。
- **根因**：操作已被用户关闭，但Promise成功继续；对话框generation与路由owner未贯穿认证后的整个await链。不能用“认证请求已被远端接受”推导“旧窗口仍能接管当前UI”。
- **归属复核**：`git diff baseline -- packages/tui/src/component/dialog-provider.tsx`为空，因此明确标记**pre-existing直接调用方缺陷**，不声称由第五轮新增，也不重新打开R-011的Restore/warp原始问题。它是本轮必须核查的无参bootstrap/provider相容性链路中的确认发现，不属于DEC-005排除项。
- **影响/不修复后果**：正常延迟即可反复抢占用户当前交互窗口，关闭操作不能可靠终止该窗口的本地完成动作；按与历史R-011相同的可恢复交互稳定性问题列应改。不声称有凭据泄漏、重复认证、永久锁死或模型执行。
- **建议及原因**：在provider操作发起前捕获相应route和dialog operation owner，在每个await后的错误提示、完成跳转、clear/replace前核查；关闭/替换/导航后抑制旧UI副作用。保留认证已经成功后的必要配置刷新与R-012的共享任务语义，不因关闭一个窗口而盲目中断共享准备或重放认证。核查API key与两种OAuth完成路径，补真实宿主“dispose/refresh挂起→关闭或replace→迟到成功/失败不覆盖新窗口”，并保留未取消成功及TC-038。

- **检查项/结论**：非核心UI配置一致性。默认实际粘贴行为仍遵守晚到配置，但开关命令显示相反状态，首次点击只是写回已有的有效状态。
