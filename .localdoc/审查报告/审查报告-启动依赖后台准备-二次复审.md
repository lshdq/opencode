### R-007 [阻塞] Home 显式 workspace 准备失败丢失可取消 owner，离开后仍拒绝无关 Session 提交

- **检查项/结论**：失败作用域及恢复要求未满足；仅 Session 路由拥有完整取消链，Home 新增 bootstrap 分支没有。
- **证据**：`packages/tui/src/component/prompt/index.tsx:1016-1022` 只将本次 submission 的 `signal` 传入 bootstrap；`:983-986` 在失败后把 `submission` 设为 undefined，却没有保留该候选的路由 owner；`:166-172` 导航只能 abort 仍被 submission 引用的 controller。`context/sync.tsx:464-469` 将该信号作为 scoped failure owner，`context/preparation.tsx:45-55` 保留失败直至 owner abort。
- **根因**：任务结果失败后，调用方释放了唯一能取消它的 submission 引用，但 preparation 仍把错误作为活跃 scope 保存。`route.signal` 未参与组合，卸载 Prompt 或导航 local Session 不会清除这个错误。新 local Session 与旧 committed workspace 相同，因此不会调用另一 bootstrap 来间接替换它。
- **触发条件**：local 已准备 → Home 的 Warp 选择已有 workspace A → Enter → A 的 `/config` 返回 500 → 失败提示出现、等待状态解除 → 导航一个 local Session，再 Enter。无需 npm、插件或新 Session 自身失败。
- **只读真实宿主证据**：使用真实 app.run、默认 Prompt、`workspace.set` 命令与实际方向键/Enter；仅 HTTP 返回受控。实际结果：

  ```json
  {
    "route": {"name":"session","params":{"sessionID":"ses_local"}},
    "failed": true,
    "config": {"username":"OLD","auto_approve":true},
    "draft": "unrelated local session",
    "posts": ["http://test/sync/start", "http://test/experimental/workspace/sync-list"]
  }
  ```

  A 配置确实请求并返回 500；切到 local 后仍显示 Startup failed，**零 create/message/shell**。不是新路由配置尚未完成，也不是插件屏障未解除。
- **归属**：本轮新增 Home bootstrap 分支引入；不是 DEC-005 或无关基线问题。
- **影响/不修复后果**：离开失效候选不能恢复已就绪 context，错误会持续阻止无关的 Home/local Session 发送。只有另一个真正触发 bootstrap 的操作或重启才能间接清除，普通取消/导航无法恢复。
- **建议**：让候选及其失败明确绑定启动该候选的路由生命周期，并保留 submission 取消语义；例如将捕获的 route owner 纳入候选 signal，或采用专门的候选 owner。不能简单在 finally 无条件清除错误，否则当前失效路由的重复 Enter 又可绕过持续失败要求。补 Home 显式选择的失败/重复提交/导航 Home 与 local Session/卸载矩阵，断言离开后零残留错误且正常发送，仍保留真正全局失败。

### R-008 [应改] 已离开页面的 workspace 删除回调借用新路由 signal，取消新 Session 的候选准备

- **检查项/结论**：旧异步操作跨路由生命周期，破坏新 owner 的有效任务。新增 route signal 只在 DELETE 返回后才获取，不能约束旧操作。
- **证据**：`packages/tui/src/component/dialog-workspace-list.tsx:67-86` 先等待 remove，随后读取变化后的 current 与 `route.signal`，即使被删除 workspace 与新路由无关仍调用 bootstrap；`context/sync.tsx:464-469` 无条件 abort 前一个候选；`:585-586` 使被替换调用抛 AbortError。`routes/session/index.tsx:310-331` 新 Session 的 hydration signal 仍有效，因此将这个异常保存为该新 Session 的 preparation failure。
- **根因**：把“删除之后刷新发现信息”作为无条件替换执行 context 的操作，而且绑定的是完成时的新路由 owner。旧对话框卸载不阻止回调；删除 A 的回调没有权力用旧 committed local context 替换新路由 C 的候选。
- **触发条件**：local 已就绪，在 Workspaces 删除 A，DELETE 挂起 → 关闭对话框、进入 workspace C 的 Session，C config 挂起并 Enter 等待 → A 删除返回成功 → C config 随后正常成功。
- **只读真实宿主证据**：实际 `workspace.list` 和两次 `session.delete` 命令发出 DELETE，Escape 后导航 C。结果：

  ```json
  {
    "route": {"name":"session","params":{"sessionID":"ses_C"}},
    "failed": true,
    "config": {"username":"OLD"},
    "directory": "/tmp/opencode/packages/tui",
    "draft": "C must prepare",
    "configRequests": [
      "http://test/config?directory=%2Ftmp%2Fopencode%2Fpackages%2Ftui",
      "http://test/config?workspace=C&directory=%2Ftmp%2Fopencode%2Fpackages%2Ftui",
      "http://test/config?directory=%2Ftmp%2Fopencode%2Fpackages%2Ftui"
    ]
  }
  ```

  C 没有配置失败，但旧删除结束后多出一次 local config 请求，C 响应被作废，新路由显示 Startup failed，零 create/message/shell。
- **归属**：旧删除回调此前也缺少导航约束，但本轮 bootstrap 的替换 owner/失败屏障使其确定取消并毒化新候选；是本轮相邻生命周期回归。
- **影响/不修复后果**：一次慢 DELETE 即可让正常 C 的待发送草稿失败并持续被挡，需要离开/重进恢复；如果被替换 C IO 仍不 settle，外层 hydration 还会继续等待它。本轮按可重新进入恢复的局部可用性问题列“应改”，不冒称进程永久死锁或内存耗尽。
- **建议**：在删除发起前确定操作 owner，完成后先验证其仍有权改变当前路由/context；对已离开、且删除的不是新执行目标的操作仅做安全发现更新，不无条件替换新候选。对于确实删除当前 context 的场景仍需按 DEC-009 在新 Home owner 下建立 local 屏障。补 DELETE deferred × 导航 local/C × 新 config 先/后完成的宿主测试，确保旧删除不取消新准备或清除/设置无关错误。
