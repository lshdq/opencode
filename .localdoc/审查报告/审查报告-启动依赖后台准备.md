## 4. 经复核成立的发现

### R-001 [阻塞] 等待中的 shell 提交按 Escape 不取消，随后反而作为模型消息发出

- **证据**：`packages/tui/src/component/prompt/index.tsx:407-417` 的取消只位于 `session.interrupt`；`:867-872` 的 textarea 级 shell Escape 绑定只执行 `setStore("mode", "normal")`；`:997-1001` 进入等待；`:1100-1135` 就绪后根据此时 mode 选择 shell 或模型路径。
- **触发路径**：启动配置/插件未就绪 → 空输入按 `!` 进入 shell 模式 → 输入命令并 Enter → 出现 “Waiting for startup… … to cancel” → 按一次 Escape → 释放准备。
- **根因**：更具体的 shell Escape 绑定消费按键，没有调用 `cancelSubmission()`；模式变化不属于 `onContentChange` 的文本变化，原等待仍有效。等待后读取可变 mode，现已变成 normal。
- **实际复核结果**：Escape 后 `waiting=true`；随后出现 `POST /session` 和 `POST /session/ses_diag/message`，正文为 `echo shell-diagnostic`；不是 `/shell`，也不是取消后零发送。
- **影响/不修复后果**：违反明确的取消要求，用户取消后仍有模型执行和潜在工具副作用；原计划只用于 shell 的命令文本被发给模型。
- **建议**：等待时 Escape 必须优先取消提交（shell 绑定同样处理，或调整等待状态的绑定优先级）；模式切换应纳入提交意图取消/一致性规则。补真实键盘测试：shell 等待中一次 Escape，释放所有准备后 create/message/shell 均不得发生，草稿保留。

### R-002 [阻塞] 自动转移待发送草稿丢失 shell 模式，将本地命令变为模型请求

- **证据**：`packages/tui/src/context/prompt.tsx:21-31` 保存/恢复 `previous.current` 后自动 `ref.submit()`；`component/prompt/index.tsx:297-309` 中 mode 与 prompt 分开存放，`:606-618` 的 current/set 不携带或恢复实际 mode；`packages/tui/src/app.tsx:569-572` 的恢复路由同样只传 `ref.current`。
- **触发路径**：默认首页在慢插件准备期间已可输入 → `!` 进入 shell → 输入并提交，等待准备 → 插件注册 `home_prompt` 替换默认 Prompt → PromptRefProvider 自动转交草稿和 pending。
- **根因**：转移的是文本/parts，而不是完整提交意图。新 Prompt 的 `store.mode` 默认为 normal。`PromptInfo` 虽有可选 mode 字段，当前 ref.current 不从实际 store.mode 生成它，ref.set 也不恢复实际 store.mode，因此仅“类型有 mode”并未处理该问题。
- **实际复核结果**：插件替换后只发出一次请求，但目标为 `/session/ses_diag/message`，内容 `echo shell-transfer`。同样的键盘步骤，在不取消且不替换输入框的对照运行中调用 `/session/ses_diag/shell`，command 为 `echo shell-control`，排除了未进入 shell 模式的误报。
- **影响/不修复后果**：即使没有用户取消操作，后台插件完成也会改变待发送内容的执行方式；正常 shell 功能与后台输入兼容性被破坏。continue/fork 的草稿转移也使用同一不完整快照，需要同时核查。
- **建议**：草稿/待提交快照完整携带并恢复执行模式，确保 `PromptRef.current`/`set` 与实际 mode 一致；恢复 mode 后再恢复 pending。补插件替换和 continue/fork 转移的 shell 测试，断言恰好一次 `/shell` 且零 `/message`，并覆盖取消后不得复活。

### R-003 [阻塞] 已放弃的启动 fork 迟到失败永久污染全局就绪状态

- **证据**：`packages/tui/src/app.tsx:534-575` 把整个恢复闭包作为默认 fatal 任务 track；`:561-566` 只在 fork **成功 await 后**检查 disposed/route.revision；`packages/tui/src/context/preparation.tsx:25-29,43-50` 把失败永久保存并使以后所有 wait 拒绝。
- **触发路径**：`--continue --fork --prompt` → fork HTTP 已发出 → 用户导航首页/新目标，旧提交已取消 → 旧 fork 返回 HTTP 500 → 用户提交新页面草稿。
- **根因**：rejection 跳过成功路径的 revision 检查，失效路由的操作仍被当作当前应用不可恢复的启动故障；不是核心配置或插件失败。
- **实际复核结果**：导航后返回 500，当前 route 为 home，出现 `Startup failed`；再次输入 `new unrelated draft` 并提交，所有发送请求数仍为 0，草稿保留但应用不能再发送。现有 `navigation while fork HTTP request is in flight...` 仅释放成功响应；现有 fork 失败测试则未离开原目标。
- **影响/不修复后果**：用户已经取消/离开的恢复操作能够迟到锁死整个交互会话，只有重启才能恢复；与抑制用户导航后的迟到恢复不一致。
- **建议**：区分应用必需准备与路由恢复任务；在恢复的错误路径也检查取消/销毁/路由版本，失效操作的错误不得设置全局 fatal。不要简单吞掉仍有效的 fork 错误，也不要削弱 Sync/认证/插件屏障。补“fork 在途导航后失败，随后新草稿能正常发送一次”的真实宿主回归。

### R-004 [应改] 离开会话后，旧 hydration 仍阻塞其他页面的所有新提交

- **证据**：`packages/tui/src/routes/session/index.tsx:287-301,294-336` 将会话 hydration 加入应用级 preparation；cleanup 只设 disposed，不能让正在 await 的请求结束；`packages/tui/src/context/preparation.tsx:17-31,43-46` 仅在 Promise settle 后移除并对全部 pending 做 Promise.all；新页面的 Prompt 在 `component/prompt/index.tsx:998` 等待同一集合。
- **触发路径**：启动已经完成 → 切换到会话 A，A 的 session.get/后续 hydration 很慢 → 在响应前返回首页或切换 B → 提交新草稿。
- **根因**：路由局部加载被提升为全局阻塞任务，却没有随路由失效退出屏障的机制。disposed 防止了部分迟到写入，但不会解除等待依赖。
- **实际复核结果**：挂起 `/session/ses_old`，导航 home 后提交 `new route draft`，出现 startup 等待且请求数为 0；只有释放已经卸载的旧会话 GET 后，新首页才创建会话并发送。这不是后台插件尚未完成造成的：该诊断先等待 pluginHost.start 和首页输入就绪后才导航。
- **影响/不修复后果**：一个已放弃会话的延迟转嫁到所有新提交；旧请求不 settle 时等待持续。每次访问未完成的会话还会增加被全局集合持有的任务，离开页面不释放，直到请求 settle 或整个 provider dispose；无需高并发，一个慢请求即可触发。
- **建议**：让会话级屏障绑定对应路由/会话生命周期；切换时取消或使旧任务从有效等待中完成，并阻止后续迟到写入，但不能取消共享 npm/插件准备。**仅从 pending Set 删除不充分**：已经进入的 wait 捕获了 Promise.all 快照，也必须能从该旧等待中脱离。补“旧会话 GET 或 messages 挂起，离开后新页面提交不等待旧请求”的回归。
