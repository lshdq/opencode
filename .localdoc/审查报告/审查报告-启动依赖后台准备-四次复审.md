## 4. 经复核成立的发现

### R-012 [应改] 实例失效事件取消另一workspace的有效候选，正常配置成功后仍持续拒绝该Session提交

- **检查项/结论**：共享准备入口的所有权与失败收敛不完整。实例刷新不是用户切换目的地，不能以旧committed context无条件替换正在进入的另一个workspace。
- **代码证据**：
  - `packages/tui/src/context/sync.tsx:187-192`：`server.instance.disposed`仅检查removed，随后无参`bootstrap()`；不检查事件来源是否与当前候选有关，也不保留候选目的地。
  - 同文件`:476-486`：每次bootstrap无条件`preparing?.abort()`，无参调用从`project.workspace.current()`选取仍保留的旧context；`:600-601`被替换调用最终抛出AbortError。
  - `packages/tui/src/routes/session/index.tsx:309-331`：候选C被替换不等于C的hydration owner离开；此时错误继续抛给仍有效的Session preparation，成为持续失败。
  - `packages/tui/src/context/preparation.tsx:45-55,69-76`：保留该有效owner的失败，之后Enter继续拒绝，直至离开路由。这里的持续失败规则本身是必要约束，错误在于无归属刷新取消了有效候选。
- **真实可达来源**：`context/event.ts:12-19`将全局事件和directory/workspace元数据交给订阅者，没有过滤掉这个事件；`packages/opencode/src/project/instance-store.ts:79-98,126-141`在实例dispose/reload时实际发布该事件。既有provider连接链路会调用`instance.dispose()`（`component/dialog-provider.tsx:281-283,332-334,405-406`），服务器HTTP生命周期也支持dispose/reload（`opencode/src/server/routes/instance/httpapi/lifecycle.ts:23-50`）。因此原实例刷新/释放的通知在用户已经进入C但C尚未准备完成时到达，是实际可能的异步交错，不要求损坏事件或不可能输入。
- **触发条件**：local已准备 → 进入workspace C的Session，C `/config`挂起 → 输入并Enter等待 → 收到local的`server.instance.disposed` → 事件启动local bootstrap并取消C候选 → C配置正常成功返回。
- **本轮只读真实宿主诊断**：在`packages/tui`执行一次`bun -e '<inline diagnostic>'`。实际app.run、Textarea/Enter、Solid上下文、事件订阅与SDK请求构造；仅HTTP及事件边界受控。没有让C返回失败。输出：

  ```json
  {
    "route": {"name":"session","params":{"sessionID":"ses_C"}},
    "configs": [null,"C",null],
    "config": "LOCAL",
    "path": "/tmp/opencode/packages/tui",
    "failed": true,
    "posts": [],
    "draft": "C must survive refresh"
  }
  ```

  `configs`为实际`/config`请求query中的workspace，null表示local；`failed`为真实渲染树包含`Startup failed`。诊断在故障出现后再次Enter，仍零POST。C的HTTP响应为成功`{"username":"C"}`，没有被发布；额外local请求由事件触发。
- **根因**：累计改动将bootstrap变为全局可替换候选，但原事件调用方没有迁移为有来源/候选归属的刷新。取消的是内层bootstrap owner，而不是仍在使用它的C路由owner，因而把内部抢占变成C的有效业务准备失败。
- **归属**：无参事件刷新是**pre-existing调用方**；新的候选替换和持续失败机制使其形成当前确定回归，位于本次修改的`sync.tsx`及直接影响链内。不是重复打开R-008的DELETE入口，也不是DEC-005。
- **影响/不修复后果**：一次原实例的释放通知即可使没有配置故障的C停止准备和发送，重复Enter无法恢复，需要离开再进入。若旧C IO尚未结束，外层hydration仍等待它；成功结束后转为持续错误。请求目标防线仍阻止错误执行，因此按可恢复的局部可用性问题列**应改**，不声称进程永久锁死或数据损坏。
- **建议及修改原因**：区分“显式候选切换”和“实例失效刷新”。事件必须根据实际directory/workspace及候选状态处理：与候选无关的旧context刷新不得取消候选；确实影响当前候选时，应在其既有生命周期内重建/协调完整准备，不能退回旧committed目的地并把内部supersession当作路由配置失败。不要简单吞掉所有AbortError后放行，否则会削弱R-005/R-006的完整上下文门禁。同步核查provider连接后的显式bootstrap与同次dispose事件重复触发的相容性。
- **建议持久化证明**：加入真实宿主local→C config deferred→local disposed→C成功的测试，断言不产生无关local候选覆盖、C恰好发送且无残留失败；另覆盖事件确实针对候选的协调路径及其失败/导航取消。保留R-001～011全部回归，不需要真实外部provider、npm或远端workspace。
