## 4. 经复核成立的发现

### R-010 [阻塞] 删除当前 workspace 后，取消 local 恢复屏障会使 Home 重新向已删除 workspace 创建会话

- **检查项/结论**：删除恢复及执行上下文有效性未满足；已删除的 committed context 不能作为候选取消后的安全兜底。
- **证据**：`packages/tui/src/component/dialog-workspace-list.tsx:83-94` 和 `dialog-session-list.tsx:173-187` 将替代 local 准备绑定到新 Home 的 route signal；`context/route.tsx:47-51` 每次导航使该 owner 失效；`context/preparation.tsx:23-29` 解除等待/失败；`context/project.tsx:79-84` 发现刷新保留已删除 A 的 committed workspace/path。`component/prompt/index.tsx:1039-1055` 仅对已有 Session 校验 workspace 就绪/连接状态，Home 在 `:1061-1079` 无条件以 retained `sync.workspace` 和 directory 创建。真实可达导航命令为 `app.tsx:632-642` 的 `session.new`。
- **根因**：候选取消保留旧完整快照解决了 R-006，但删除已经使该快照失效。当前实现只依赖一个可随 Home 导航取消的 local 屏障，没有独立记录“这个旧执行目标已删除/不可用”，也没有让后续 Home 重新建立必要的 local 准备。
- **触发条件**：A 已完整准备 → Workspaces 删除当前 A，DELETE 成功 → 自动 Home、local `/config` 仍 pending → Escape 关闭 Workspaces → 执行 New session（同样导航 Home，轮换 signal）→ 输入并 Enter。无需 local 请求失败、npm 故障或另一个 workspace。
- **本轮只读真实宿主诊断**：包目录 `bun -e '<inline diagnostic>'`，实际 app.run、OpenTUI 对话框/Enter、`workspace.list` / `session.delete` / `session.new` 命令，SDK 请求由可控 fetch 接收。删除后发现 list/status 都为空，local config 始终未释放，输出：

  ```json
  {
    "removed": true,
    "route": {"name":"home"},
    "posts": [
      {"url":"http://test/session?directory=%2Fworkspace-A&workspace=A","config":"A","path":"/workspace-A"},
      {"url":"http://test/session/ses_created/message","config":"A","path":"/workspace-A"}
    ],
    "config":"A",
    "path":"/workspace-A",
    "failed":false,
    "localStillPending":true
  }
  ```

- **成立性复核**：不是仅旧路径标签残留，实际 create query 同时带已删除 A 和 A directory；不是全局插件未准备；没有伪造一次 local 配置成功。两个删除入口具有相同的新 Home owner/local bootstrap 结构；本轮动态证据来自 Workspaces 入口，恢复入口按相同活动链路静态确认。
- **归属**：第三轮删除恢复与累计 retained-context 策略的相邻回归，区别于 R-009 原始“未建立 local bootstrap”。
- **影响/不修复后果**：用户明确删除工作区后，常规 New session 仍向失效目标创建/发送，绕过必要 local 准备，无法保证正常恢复。受控响应没有真实创建远端会话；错误 SDK 请求本身已足以证明核心目标一致性错误。
- **建议及原因**：将“已删除执行上下文不可再使用”与可取消候选 owner 分开管理；后续 Home 要么建立新的完整 local 准备，要么明确禁止提交直到有效 context 就绪。不能只清空 workspace/path 造成部分发布，也不能把所有旧操作重新提升为不可取消全局任务而复发 R-004/R-008。对两个入口补 DELETE 成功后 local pending/失败 × New session/离开再回 Home × normal/shell 回归，断言 local 就绪前零执行、永不再发向 A，并保留切到 C 不受旧任务阻塞的回归。

### R-011 [应改] Restore/warp 在后续 reminder 等待期间失去 route owner，迟到完成仍重新打开 Sessions

- **检查项/结论**：取消/导航后的异步回调隔离不完整；新增 signal 仅保护 warp 与 bootstrap 前半段。
- **证据**：`packages/tui/src/component/dialog-workspace-create.tsx:135-145` 做最后一次 signal 检查，随后 `:149-162` await `promptAsync`、`:165` await workspace/session 刷新，`:167-171` 无条件 `done()` 或 `dialog.clear()`。恢复调用方 `dialog-session-list.tsx:107-109,137-149` 传入原 route signal，但 `done: list` 会重新 `dialog.replace(() => <DialogSessionList />)`。`dialog-session-delete-failed.tsx:47` 的 disposed 只保护该组件自己的 confirm 后续，不能保护已经进入 Restore 的独立 warp 闭包。
- **根因**：把“bootstrap 后检查过 owner”当成后续整个异步链的授权。用户可以在 reminder 请求或刷新尚未结束时关闭对话框并导航，之后的 callback 仍然操作当前 dialog。
- **触发条件**：A 的 session.delete 返回错误 → 真实 Failed to Delete Session 中方向键选 Restore → Choose workspace 选 None/local → warp 和 local 准备成功，但 synthetic `prompt_async` 挂起 → Escape 关闭选择窗口并进入 C → 释放旧 reminder 请求。
- **本轮只读真实宿主诊断**：全部上述 UI/命令、Solid 生命周期与 SDK 为真实实现，只有 HTTP/事件受控；输出：

  ```json
  {
    "route":{"name":"session","params":{"sessionID":"ses_C"}},
    "before":false,
    "after":true,
    "config":"C",
    "requests":[
      "POST http://test/experimental/workspace/warp",
      "POST http://test/session/ses_A/prompt_async"
    ]
  }
  ```

  `before/after` 是旧 reminder 完成前后真实 render tree 是否存在 Sessions 对话框。C 已配置完成；用户没有重新发出 session.list，旧窗口仍复活。
