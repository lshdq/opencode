## 4. 经复核成立的发现

### R-01 [阻塞] 正常 WAL 初生的公开句柄窗口没有关闭

- **证据**：`packages/core/src/database/sqlite-permissions.ts:16-20` 只以 `create:false` 处理侧文件；不存在时 `packages/util/src/file-mode.ts:30-36` 直接返回。随后 `sqlite.bun.ts:98-103` / `sqlite.node.ts:93-96` 先由 SQLite 执行 WAL pragma 和查询、创建 WAL/SHM，再逐个启动 PowerShell 收紧。
- **根因**：“在第一条凭据 SQL 之前改 DACL”不等于“在创建时阻止其他主体取得句柄”。Windows 在打开文件时给句柄授予访问权，收紧路径上的 DACL 不撤销已打开句柄的访问权。SQLite Windows VFS 的普通打开使用 `FILE_SHARE_READ | FILE_SHARE_WRITE`，没有以独占句柄覆盖这一窗口。
- **可达触发链**：用户将 `OPENCODE_DB`/数据库路径放在对其他本地用户授予可继承 Read 的目录（无需赋予修改或删除权限）→正常新建或末连接关闭后的正常 reopen→SQLite 创建尚无秘密的 `-wal`→其他主体此时打开并保留只读句柄→PS 将 DACL 改为当前 SID→正式 client 写入 credential 页到同一个 WAL→旧句柄仍能读取随后写入的凭据。此链没有 journal_mode 手工切换、外部 SQLite writer、重解析点替换或高权限假设。
- **窗口与资源**：WAL 创建到保护之间至少包括独立 PS 启动/执行；SHM 还排在 WAL 后。开发记录已有 PS5.1 单次389–515ms级样本，不是仅数条同步指令的窗口。保留句柄者可持续读到其关闭/文件生命周期结束；后续 DACL 验证全部通过也不能回收该权限。
- **影响**：违反 TC-007/008 和本轮强调的正常 WAL 初生边界；敏感 credential 内容可以泄露。不能以“写秘密前 DACL 已正确”或“只检查 client 返回后 DACL”解除此阻塞。
- **修法**：让支持的正常 WAL/SHM 从创建起就 private。可优先验证在受控、协同的打开流程中安全预创建缺失的空侧文件，再让两种 SQLite driver 打开已有文件的可行性；必须保持已有侧文件不截断、readonly/create flags、关闭/重开与并发语义。若驱动会自行替换而不能保证，则使用真正创建时安全的 VFS，或经明确配置使用专用安全目录/拒绝不安全位置。**不得修改任意父目录 ACL，不得用事后补 chmod 宣称解决。**
- **需补证明**：用例要观察第一次可打开的侧文件，而不只是获取 client 后检查；加入“初生窗口取得的读取句柄不能读取随后写入秘密”的对抗性验证，涵盖 Bun/Node 与 normal reopen。第二用户或受限 token 测试未在本审查执行，不冒充实测泄露；结论依据确定的代码顺序与 Win32 访问权语义。
- **语义参考**：Microsoft Learn `File Security and Access Rights`（默认 security descriptor 继承父目录、访问检查授予 handle 权限）；SQLite 官方 `src/os_win.c` 的 `winOpen`（`OPEN_ALWAYS`、共享读写、`CreateFileW` security attributes 为 NULL）。已读取外部源码用于核对 VFS 语义，不将 master 源码冒充本机二进制的逐字 build provenance。

### R-02 [应改] 迁移排他创建后失败会留下永久阻断自动重试的空目标

- **证据**：`packages/cli/src/services/service-config.ts:89-94` 先 `FileMode.prepare(file, {exclusive:true})` 创建正式目标，随后另一个 Effect 才 `writeFileString(file, text)`；`AlreadyExists` 直接转 false。`read():135-142` 解码失败回退 `{}`，`password():154-161` 可据此生成并写入新密码。
- **根因**：排他占位被当成“迁移已提交”的标记，没有区分初始化中/已完成；两步之间及第二步失败时没有可恢复发布协议。
- **触发链**：preview/dev 等存在 legacy 配置的频道第一次迁移→正式目标已私有创建→取消、进程退出或后续写失败→留下空/不完整目标→下一次迁移收到 AlreadyExists 被跳过→读空目标返回默认配置。开发记录明确允许外部 kill 留空私有文件，但“可以正常重试”不适用于这里的 exclusive 消费者。
- **影响**：迁移的 hostname/port/env/password 不再自动恢复；可能改用默认端口、丢失服务环境配置或重新生成密码。原 legacy 尚在，人工可恢复，故不描述为不可恢复数据销毁。正常路径测试与“目标不存在的父目录”测试不覆盖此问题。
- **修法**：迁移内容先完整写到 private 临时文件，再通过保持 no-overwrite 的原子发布/现有锁机制提交；失败清理必须基于自己的所有权，不能盲删另一个并发者已接管的目标。或设计明确可识别的未完成迁移恢复协议；不能简单对任意已有目标强制覆盖。
- **需补证明**：在实际 exclusive prepare 完成后、正式写前取消，以及实际写失败后重试；断言最终继承完整旧配置且不覆盖另一个已完成目标。两个迁移入口 `migrateConfig/migrateRegistration` 都走该 helper。

### R-03 [应改] Effect 取消返回早于 ACL executor 的 close 完成

- **证据**：`packages/util/src/fs-util.ts:121-124,155-158`，`packages/cli/src/services/service-config.ts:89,122,138,149`，两 SQLite driver 等均用 `Effect.tryPromise` / `Effect.promise` 包装 `FileMode.prepare`。实际 Effect 4.0.0-rc.112 `src/internal/effect.ts:1051-1088,1102-1139` 中，这两种构造器的取消 finalizer 只调用 `AbortController.abort()`，没有等待被包装 Promise settle。
- **独立只读代码探针**：本会话以 Bun1.4.2 从 util 包运行内存 `-e`，通过真实 `FileModeWindows.execute('[System.Threading.Thread]::Sleep(60000)', {}, {signal})` 启动一个不访问文件、不产生后代的 ACL 宿主；1秒后 `Fiber.interrupt`，记录 executor 的 finally 是否执行，再显式 await 同一 Promise。实际输出依次为 `{"afterFiberInterrupt":false}`、`{"afterHostClose":true}`；命令退出0。探针没有修改生产/测试或任何目标文件。
- **根因**：executor 的 Promise 确实等待 `child.close`，但外层 Effect 在中断时放弃等待该 Promise，绕过了接线所声称的“调用失败返回前已回收宿主及管道”边界。直接调用 Promise + AbortController 的现有测试只能证明内层。
- **触发链/影响**：服务配置操作、FSUtil 写入或 DB layer 权限准备时 Fiber 被取消→外层 finalizer/路径清理或重试开始→executor 仍未完成 close 回收。可能与 Windows 文件句柄释放/ACL 操作尾部交叠，造成取消后的清理及重试竞态。仍存在10秒超时和 kill，不把此项夸大为已证实的无限进程泄漏，也不声称探针证明内核进程在那一瞬间必然仍活着。
- **修法**：给这类受管理 Promise 提供 Effect 取消 finalizer：先 abort，再以不可中断的清理阶段等待同一个执行 Promise settle/close（错误只在清理 join 中归并）；复用在各调用点。可以用已核对存在的 `Effect.callback` 取消 effect，或等价的 scoped acquire/release 包装。不要简单把整个10秒权限操作都设为不可取消。
- **需补证明**：真实 FSUtil/ServiceConfig/SQLite 接线的 Fiber 中断测试，断言中断完成后 executor 已 close 且 fixture 可立即清理/重试；不只检查直接 Promise 的 abort。

### R-04 [可选] 同一次权限准备有可量化的重复 PowerShell 启动

- **证据**：SQLite `prepareDatabase:12-13` 加 driver 返回前的 `protectSidecars`：有现存 WAL/SHM 时主库1次、侧文件前2次、后2次，共5次；正常新建/重开通常3次。`ServiceConfig.options():122-126` 两个现存文件分别启动宿主；`set/unset` 随后再次 `read()` 同一配置（例如 `set:218-220`）。
- **影响依据**：开发记录的 PS5.1 实测单次 `[515,389,395,388]ms`，已有侧文件的两次额外宿主是约0.8秒量级样本成本；该数值不是本审查重测或全应用百分比。短时多 CLI/连接初始化也按文件数放大宿主开销。
- **建议及边界**：在同一阶段批量校验多文件、在单个配置操作内部复用已读取结果；保持每个文件错误归属、有限总超时、取消回收和身份校验。无需常驻 PS 框架、全局权限缓存，也不要以减少次数为由引入 R-01 的不安全简化。当前没有运行期高 QPS/不可用证据，故仅列可选。
