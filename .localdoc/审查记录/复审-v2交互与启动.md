### 原生方法、回调和 cleanup 追踪

1. Prompt 的 textarea ref 在 `index.tsx:1852` 调用 `bindPromptUndo`；binder 先读取 `input.extmarks`，让 OpenTUI 的懒包装先安装，再保存其方法并安装外层 capture/record/step。不是在 Extmarks 安装前保存了错误的原始方法。
2. 锁定依赖中 `EditBufferRenderable.insertText` 先调用 `editorView.deleteSelectedText`、再调用 `editBuffer.insertText`（`chunk-bun-bb3k0yt8.js:5986-5991`）。所以替换选区/展开本来就是两个 native 步骤；现有两次 undo 测试不是为了掩盖步骤数而放宽预期。
3. Extmarks 的 deleteSelectedText 包装先保存 snapshot，原生删除后调整 mark（`chunk-bun-9gqvxy8c.js:9916-9934`）；F-02 当前不在进入该包装前手工删 mark。Prompt capture 同步现存 extmark/part，并复制可变位置、共享不可变 payload 字符串。
4. Undo/redo 先运行保存的 Extmarks/native 操作，再用配对 snapshot 重建 Prompt metadata/extmarks；`restoreExtmarksFromPrompt` 同时使旧 submission 意图失效。同步 JS 调用内没有 await；现有 copy/POST 测试没有观察到“正确配对时”中间状态被提交。但 **是否真的一一配对不能由文本相等判断，R-03 即证据**。
5. `setText/setTextOwned/clear/clearHistory` 清平行历史；`resetComposer` 先置空 store/map，再让原生 clear 统一清文本和历史，不再提前单独 clear mark。重置及新草稿中的同名字面标签有实际 copy/POST 测试。
6. ref 所注册的 Solid cleanup 清空 undo/redo 数组并恢复 buffer/editorView 方法；Prompt owner cleanup 取消准备并 stash 草稿，OpenTUI destroy 再回收自己的 editor/extmarks。已沿真实导航/退出/重挂载测试检查，不把原生内存整体有界作为结论。

## 4. 确认发现

### R-03 [阻塞] 向前 Delete 在末尾产生原生 undo 步骤，文本相等过滤却漏记元数据，撤销后实际发送标签

**检查项：TC-010 / DEC-011 撤销元数据与原生编辑步骤一致性。**

- **证据位置**：`packages/tui/src/component/prompt/undo.ts:34-46`，尤其 `:43` 的 `if (!replace && text === input.plainText) return`；`deleteChar` 经此包装（`:75`），撤销从元数据栈弹出另一条步骤（`:59-69`）。实际可达快捷键为 `packages/tui/src/config/keybind.ts:232` 的 `ctrl+d,delete,shift+delete`。错误 metadata 影响 `prompt/index.tsx:1159,1436-1442,1878-1887` 的提交/复制展开。
- **根因**：注释“其他无文本变化的操作不产生 native 步骤”与锁定 OpenTUI 0.5.10 的真实语义不符。光标位于文本末尾时，`editBuffer.deleteChar()` 即便不改变文本，仍产生一次原生 undo 记录。binder 已调用 action，却因前后文本相等没有 push snapshot；下次 undo 消耗的是 Delete 的原生步骤，弹出的却是上一次 paste 的“粘贴前”metadata。
- **真实用户复现**（无极端数据量、无模拟内部历史）：
  1. Home 的真实 Prompt 配置 `prompt.paste=compact`，bracketed paste `AAA1\nAAA2\nAAA3`，得到 `[Pasted ~3 lines] `，光标在末尾。
  2. 按 **Ctrl+D**（默认向前 Delete），文本没有变化。
  3. 按 **Ctrl+Z**。文本仍是该占位符，但 extmark 数从 1 变 0，`canUndo()` 已为 false。
  4. 全选调用生产 `Selection.copy`，再清选区按 Enter。fixture 记录的实际剪贴板内容和真实 Client `POST /api/session/<id>/prompt` 均为标签字面量，而不是 A 三行正文。
- **本轮隔离实测输出**：

  ```text
  AFTER_DELETE {"text":"[Pasted ~3 lines] ","at":18,"marks":1}
  AFTER_UNDO {"before":"[Pasted ~3 lines] ","text":"[Pasted ~3 lines] ","marks":0,"canUndo":false}
  COPIED ["[Pasted ~3 lines] "]
  POST [{"id":"<fixture生成ID>","text":"[Pasted ~3 lines] ","files":[],"agents":[],"delivery":"steer"}]
  ```

- **独立底层对照**：真实 `TextareaRenderable` 上执行 `insertText("A") → deleteChar()`，有/无 binder 分别调用 undo：

  ```text
  无 binder：第一次 undo text="A", canUndo=true；第二次 undo text="", canUndo=false。
  有 binder：第一次 undo text="A", metadata="before", canUndo=false；第二次 undo=null。
  ```

  这直接证明 Delete 确实增加了 native 步骤，不是误用 mockInput 或因 native undo 没完成而读取过早。初次按键探针误用小写 `pressKey("delete")` 输入了字母，已排除，不作为问题证据；最终反例使用实际默认绑定 Ctrl+D。
- **影响与严重度理由**：普通 Delete 键操作足以让占位符的隐藏文本被静默丢弃，并实际提交错误正文；还提前耗尽可用的平行 undo 历史。属于核心数据正确性阻塞，发生在远小于 256 步的窗口内。该 native 无变化步骤语义虽来自既有依赖，但错误过滤和丢载荷来自本次新增 binder，故不是将纯既存依赖问题转嫁本次修改。
- **建议及修改原因**：按锁定依赖的真实操作记录语义配对，不能用“文本未变化”统一判定所有非 replace 方法不记步骤。可选择在确定是 native no-op-record 的边界操作前拦截并保持文本/原生/元数据历史一致，或为确实记录步骤的操作保存对应 snapshot；不能简单让所有 no-op 都 push（空 insert/backspace 等有不同语义）。补充末尾/空缓冲区向前 Delete、连续 Delete、undo/redo、新分支、占位符后普通文本编辑的 native 与真实 Prompt 回归，并断言实际 copy/POST 载荷。不修复会继续出现标签可见而内容已丢失的错误提交。
- **为何现有测试未报警**：`prompt-undo-native.test.ts:43-57` 的 no-op 用例覆盖开头 backspace、空 insertText、零范围 deleteRange 和空 selection，**没有末尾 deleteChar**；`:16-40` 的 deleteChar 参数用例位于 `ab\ncd` 的中间，只测试确实删字符的路径。其他 255/256/257、pure metadata、expand、reset 测试也没有这一输入序列。本轮没有修改或新增测试文件。
