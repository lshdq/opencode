## 4. 确认发现（按严重度）

### R-01 [阻塞] 剪切撤销按可见文本反查，恢复了另一段隐藏载荷

- **证据**：`packages/tui/src/component/prompt/index.tsx:1853-1861`；相关记录写入 `:1871-1875`，同名占位符生成 `:1498-1509`，真正发送展开 `:1156-1164`。
- **根因**：`cutHistory.findLast` 仅以 undo 前后 `plainText` 匹配历史项，没有绑定原生 undo 的操作位置/身份。不同三行粘贴内容都显示 `[Pasted ~3 lines] `，其“占位符→空文本”剪切历史完全同形。撤销较早剪切时仍匹配最后一次剪切，把它的 `pasted` 元数据和 extmark 写回较早文本。
- **可达触发链**（真实 App / Prompt / OpenTUI，不复制被测逻辑）：
  1. Home 使用 `prompt.paste=compact`，粘贴 `AAA1\nAAA2\nAAA3`，全选并调用实际 `Selection.cut`。
  2. 再粘贴 `BBB1\nBBB2\nBBB3`，全选并剪切。
  3. 连续 undo 三次：撤销 B 剪切、撤销 B 粘贴、撤销 A 剪切。
  4. 第三次应恢复 A；实际可见占位符恢复，但 `getClipboardText(input.plainText)` 得到 **B**。
- **本轮隔离执行输出**：
  ```text
  CUTS ["AAA1\nAAA2\nAAA3 ","BBB1\nBBB2\nBBB3 "]
  UNDO 0 true
  STATE {"text":"[Pasted ~3 lines] ","expanded":"BBB1\nBBB2\nBBB3 "}
  UNDO 1 true
  STATE {"text":"","expanded":""}
  UNDO 2 true
  STATE {"text":"[Pasted ~3 lines] ","expanded":"BBB1\nBBB2\nBBB3 "}
  ```
- **影响**：违背“粘贴占位符和撤销正确”的核心验收；用户看不到载荷替换。再次复制得到 B，后续提交也会按恢复后的错误 `pasted`/extmark 展开为 B，而非用户撤销恢复的 A。属于静默内容错误，不是显示样式问题。
- **建议**：将并行附件元数据与原生 undo/redo 的真实操作顺序/身份绑定，正确维护 redo 分支及普通编辑穿插，不能继续用文本相等识别历史事件。增加两个同名 placeholder、多个连续 undo/redo、分支编辑的回归，并断言最后实际 `/prompt` 正文或剪贴板载荷。
- **测试质量缺口**：`test/prompt-cut-feature.test.ts:35-61` 只使用同一个 payload 的剪切→undo→redo→undo→再剪切，不能区分误匹配另一历史项。现有测试全部通过并不能证明多条历史正确。

### R-02 [应改] Home `/cd` 过期响应留下假的目标目录标签

- **证据**：`packages/tui/src/component/prompt/index.tsx:282-295`，尤其 `:292` 提前返回；展示链 `:1659-1665`，提交位置选择 `:1280-1285`。
- **根因**：新 revision guard 正确阻止迟到的 `/cd` 改写当前 Location，但提前返回没有清理本请求设置的 `pendingDirectory`。页脚优先展示 pendingDirectory，提交却读取未改变的 `currentLocation.ref`，二者永久分叉，直到再次目录操作或卸载。
- **可达触发链**：Home 执行 `/cd <目标>` → fixture gate 暂停该目标 `/api/location` → 等请求实际进入后在已清空的 composer 输入 `new draft` → 放行成功响应 → revision 不同，跳过 Location 更新和 pending 清理 → 明确再次 Enter 提交。
- **本轮隔离执行输出**：
  ```text
  CD_RESULT {"footerStillTarget":true,"draft":"new draft"}
  CREATE_LOCATION {"directory":"/tmp/opencode/packages/tui"}
  DISPLAYED_TARGET D:\tmp\opencode\packages\tui\review-other
  ```
  目标路径通过当前 Windows `path.resolve(directory, "review-other")` 生成；原位置取仓库既有 fixture 的 directory。捕获的是真实客户端 `POST /api/session` body，fixture 随后拒绝创建，未调用真实模型/服务。
- **影响**：开始输入下一条草稿是普通操作；界面宣称的工作目录与实际下一次创建/执行目录不符，用户无法根据页脚判断提示将作用于哪个工程。这里只报告状态不一致，不反对 DEC-007 对迟到结果的取消语义。
- **建议**：以目录请求身份管理 pending 状态；过期/取消/失败完成时仅清理本请求仍拥有的 pendingDirectory，不能清掉后续 `/cd` 的新 pending。允许取消旧目录变更时，页脚应恢复实际 Location。增加“请求在途编辑草稿→响应结束→页脚与实际创建目录一致”及两个 `/cd` 乱序完成测试。
- **测试质量缺口**：`prompt-command-catalog.test.ts:106-114` 验证的是已有 Session 的 `/move`，没有触及 Home `/cd` GET 的新增 revision guard；现有 navigation/admission 测试也不是此目录标签生命周期。
