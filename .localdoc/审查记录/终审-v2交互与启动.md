## 4. 唯一确认发现

### R-04 [应改] 光标导航恢复：virtual mark内部跳转的失效被外层vertical覆盖，撤销后desired-column错误

**证据**：`packages/tui/src/component/prompt/undo.ts:187-195`，尤其action前缓存 `previous`、action后无条件沿用旧anchor/delta；`:199-202,214-218` 的navigate失效；`:156-164` 按净行差重放。需求依据是本次重点caret核查及源旁 `原生撤销契约.md:18-21` 的desired-column恢复说明，不涉及native checkpoint数量。

**真实可达路径**：Prompt默认方向键 → `prompt/index.tsx:1057-1070,1093-1108` → `TextareaRenderable.moveCursorUp/Down` → owned `vertical` → OpenTUI extmarks `moveUpVisual/moveDownVisual`。落在virtual mark内部时，OpenTUI用 `editorView.setCursorByOffset` 跳到边界（`chunk-bun-9gqvxy8c.js:9687-9710`），这会改变native的desired-column。binder的navigate虽将navigation置空，外层vertical仍使用action前的previous重新覆盖，误把跳转前后当作同一连续导航链。

**确认复现（普通短草稿，0-based行列）**：

1. 真实Session Prompt插入 `abcdefghijklmnopqrst\nx\n`，bracketed paste三行 `AAA1\nAAA2\nAAA3` 得到实际payload-bearing `[Pasted ~3 lines] `，后接 `\nabcdefghijklmnopqrst`。
2. 将caret定位到第0行第8列，按默认 **Down、Down、Up**。实际路径为 `(1,1) → (2,17) → (1,1)`。第二次Down被virtual mark吸附到17列；因此此时native desired-column是17。
3. 对照路径直接再按Up，真实Prompt得到 **(0,17)**。
4. 从同一起点重走Down、Down、Up，输入 `!`，按 **Ctrl+Z**，再按 **Up**。撤销后立即caret仍为(1,1)、文本正确，但Up得到 **(0,8)**，而不是编辑前导航状态的(0,17)。

本轮 `bun -e` 实际App、默认keymap、`mockInput.pressArrow` 的关键输出：

```json
{
  "observations": [
    {
      "undo": false,
      "path": [{"row":1,"col":1,"offset":22},{"row":2,"col":17,"offset":40},{"row":1,"col":1,"offset":22}],
      "before": {"row":1,"col":1,"offset":22},
      "restored": {"row":1,"col":1,"offset":22},
      "next": {"row":0,"col":17,"offset":17}
    },
    {
      "undo": true,
      "path": [{"row":1,"col":1,"offset":22},{"row":2,"col":17,"offset":40},{"row":1,"col":1,"offset":22}],
      "before": {"row":1,"col":1,"offset":22},
      "restored": {"row":1,"col":1,"offset":22},
      "next": {"row":0,"col":8,"offset":8}
    }
  ],
  "copied": ["abcdefghijklmnopqrst\nx\nAAA1\nAAA2\nAAA3 \nabcdefghijklmnopqrst"],
  "POST.text": "abcdefghijklmnopqrst\nx\nAAA1\nAAA2\nAAA3 \nabcdefghijklmnopqrst"

```

**根因**：保存的anchor仍是初始 `(0,8)`、delta是净 `+1`；恢复时只重放一次Down到短行。它无法还原曾经过virtual mark而把desired-column改为17的事实。最终可见caret比较相等，`:163` 的fallback不会发现丢失的导航状态。

**影响/分级**：普通多行草稿中跨粘贴占位符的上下移动即可触发，undo后的后续编辑定位与保存状态不一致，需修正。该反例的文本、copy、POST隐藏载荷均保持正确；不升级为静默载荷丢失、无界资源或核心不可用的阻塞。新owned导航恢复实现的问题，不重开R-03。

**建议及原因**：让vertical识别action期间显式cursor reposition引发的导航失效；发生virtual snap时应保存新的有效导航基准/desired-column语义，不能无条件覆盖为旧previous。可利用当前已包装的真实`setCursorByOffset`边界记录失效/重置，不必fork native、读取私有ABI或恢复native undo。补充真实Prompt上述方向键组合、反向穿越和redo后再次移动的回归；同时保留纯短行、软换行、显式定位和所有payload测试。不修复则保存位置表面正确但后续Up/Down仍在错误列继续编辑。

**防误报复核**：
- 原54项正向text/caret对照没有检查此“多次导航→编辑→undo→下一次导航”的组合；现有owned desired-column测试没有virtual mark中的显式跳转，故633绿测不反驳该复现。
- 另跑底层真实Textarea有/无binder对照确认此路径的直接继续导航是17，owned恢复后是8。没有把无binder原生undo当验收oracle：单独观察到本依赖原生undo后的下一次Up为1，**并非17**。R-04依据是当前owned明确实现/测试的恢复编辑前desired-column契约，不要求复刻原生undo或将其既存缺陷包装为本轮回归。
- 首次App探针误用`pressKey("DOWN")`，实际插入字面量，已丢弃；正式证据使用实际`pressArrow("down"/"up")`，路径逐步记录如上。
