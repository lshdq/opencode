## 4. 经复核成立的问题

### R1 [应改] source.diff 被 trimEnd 截断，已保存补丁不是有效 Git patch

- **证据位置**：`packages/cli/script/windows-runtime.ts:43-54`（`execute` 对所有 stdout 执行 `trimEnd()`）；`packages/cli/script/windows-build.ts:37,43,69,104-107`（通过该 helper 获取 diff，直接写入、hash 并部署）；`docs/v2-Windows构建与迁移.md:9-10`（承诺二进制安全 source.diff）。
- **根因**：命令标量输出（version、SHA、路径）的规范化被同时用于原始补丁。`trimEnd()` 删除 diff 最后必需的换行，若最后一行含尾空白，也会改变那部分补丁数据。对截断后的文件计算 SHA256 只能证明损坏文件未变，不能证明保存的是原始 Git 输出。
- **触发条件 / 实际复现**：当前工作树有 tracked 修改时即可触发，无需异常环境或并发。审查用 `execute(["git", "diff", "--binary", "--no-ext-diff", "--no-textconv", "HEAD"], root)` 获取内容，通过 stdin 调用只读 `git apply --stat`：退出 **128**，`error: corrupt patch at <stdin>:2789`。同一内容仅补回末尾 `\n` 后退出 **0**。另直接对已有制品 `v2-2.0.12-42c52e28d6fc-1790075553646-e3548a25/source.diff` 执行 `git apply --stat`：退出 **128**，`corrupt patch ...:2288`。
- **影响**：构建和 smoke 仍可能通过，但随版本化制品/CI 上传的源差异证据不能由标准 Git patch 工具解析、复核或重放。破坏文档承诺的补丁字节保真和制品源差异可用性；不是说 exe 本身构建错误，也不是将早期制品尚未最终重建误报为发布事故。
- **建议及原因**：diff 使用原始 stdout 字节/不 trim 的专用输出路径，标量结果由各自调用方显式 trim；不要仅在写文件时补一个换行，因为被删除的尾空白也需要保留。新增真实临时 Git 仓库的回归，断言保存内容与原始 `git diff --binary` 字节相同并可 `git apply --stat`/适当的 `--check`，覆盖文本、尾空白及 binary diff。最终重建必须产出修复后的 diff 并重新核验 hash，否则后续仍会生成同样不可用的证据文件。
