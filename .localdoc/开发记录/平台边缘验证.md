## 实测结果与迁移结论

### 1. spawn / kill watchdog：保留官方
- 对照旧 fork `packages/core/src/cross-spawn-spawner.ts`：旧补丁包含 30 秒 spawn watchdog、2 秒 exit grace、5 秒 kill await。
- v2 官方已经使用 `overlapped` stdio、exit/close 分离、一秒 output deadline、`taskkill /pid ... /T /F` 与 `forceKillAfter`；本次**不修改**官方实现。
- 实测新增 Windows 用例：Bun 1.4.2 与 Node 24.20.0 分别作为 wrapper/child；正常退出且 detached 子孙持管道时有界完成，foreground stdout/stderr 不丢，scope 关闭后 descendant 仍存活；测试自有 stop 协议随后回收。
- live wrapper 的整树 kill、fiber interrupt/scope release、missing executable/invalid cwd 共 10 次失败路径通过。不存在的 exe 在 Windows 可能由 cross-spawn 经 cmd 返回非零码，而非 spawn reject；测试接受这两种既有语义。
- 没有复现 spawn/kill callback 丢失。不声称覆盖 OS API 卡死、极端资源耗尽或所有第三方 shell；没有把缺少计时器直接当成缺陷。
- 新 fixture 初版未设置 detached 时发现后代随 wrapper 消失，因此正式普通 shell 测例按官方 `held-stdio.cjs` 语义使用 detached 后代；没有据初版错误预期修改生产代码。

### 2. MCP orphan：非 detached 已覆盖；detached helper 确认有剩余缺口
使用真实 `McpStdio.make` + `hostEnvironmentLayer` + 官方 CrossSpawnSpawner，不 mock 进程或 transport。新测试直接导入 stdio，避免整套 MCP 测试初期的无关依赖缺文件阻塞。

| Node wrapper 模式 | 真实操作 | 结果 |
|---|---|---|
| `mcp` | child ready 后调用 close；wrapper 收 stdin EOF 后退出 | close 有界、child 消失，通过 |
| `mcp-early` | wrapper ready 后主动 exit(0)，等待 onclose，再重复 close | close 有界、child 消失，通过 |
| `mcp-detached` | wrapper 创建 detached helper，stdin EOF 后退出 | close 返回，helper 仍存活；复现失败 |
| `mcp-early-detached` | wrapper 创建 detached helper，然后提前 exit(0) | onclose/close 返回，helper 仍存活；复现失败 |

- 两个 detached 场景首次实测均失败；再以显式诊断开关复跑，仍是 2 fail（6.37 秒，单例约 2.8 秒）。增加 wrapper 已退出断言后最终再跑仍为 2 fail（6.06 秒，4 assertions）。失败点是 close 后等待 1 秒仍未观察到 helper 退出，**不是 transport 超时**。
- fixture helper 本属于同一隔离 MCP fixture，但显式 detached；结论不能泛化成“任何非 detached MCP 子孙都会泄漏”。普通非 detached 用例在当前 Windows/Bun 路径通过；不把 Bun 内部可能的 containment 机制未经核实当成稳定公开契约。
- 测试完成时通过本 fixture 唯一 temp 中的 `stop` 文件让 helper 自退出；所有 fixture 又有 20 秒自退出上限。cleanup 只检查本 fixture 记录的 PID，不对 PID 或进程名泛杀，不执行 CIM 扫描。
- **未添加生产修复**。仅在显式 close 前先强杀 wrapper 的方案会改变现有 graceful EOF 契约，仍不能解决已经提前退出的 wrapper；不值得作为不完整小补丁迁移。
- 最小可靠运行选择：MCP command 使用保持前台的真实 server/监督 wrapper，确保 helper 不自行 detached 并在 EOF 时自行收尾。若必须支持提前退出/脱离的 owned helper，需要单独设计可持有生命周期身份的本地 containment（例如经验证的原生 Job Object 方案）与 Environment/remote seam；这超出本次条件迁移，不宣称已完成。
- 不采用进程名、CIM parent PID 周期快照或仅 PID 的事后树推断：采样可能错过短命 wrapper，也有 PID 重用误杀风险。
- 两个已知失败诊断默认显式 skip；通过 `OPENCODE_TEST_KNOWN_MCP_ORPHAN=1` 开启后是普通失败断言，**不是 expected-pass 或假定修复**。官方的 Windows orphan skip 保持原样。

### 3. Git null device：本机无需迁移 NUL 替换
- Git 版本：`2.55.0.windows.3`。
- 实际新建隔离 repo 与 `untracked 中文.txt`，通过生产 spawner 执行官方 untracked diff 参数路径：`git diff --no-index --patch/--numstat ... -- /dev/null <file>`。
- patch 返回 code 1（正常差异），包含 `--- /dev/null` 与两行 additions；numstat 为 `2\t0\t...`；stderr 为空。目录覆盖空格、中文、单引号。

- 本项验证实际 Git/argv/platform seam，不把它冒充完整 VCS plugin UI 集成测试。

### 4. fs 瞬时锁：平台原语仍返回错误，不泛化迁移旧全异常 retry
- 独立 `pwsh.exe -NoProfile -NonInteractive` 打开 `FileShare.None`，ready 握手后收到 attempt 信号再保锁 750ms，随后自动释放。未改 ACL，不触碰 DB，也没有借用日常服务文件。
- 真实 Effect `FileSystem.writeFileString` 在锁占用期间快速失败；锁解除后原内容仍为 `original`，再次写成功并读回 `replacement`。
- 结论：实际 sharing lock 仍会造成一次调用失败，不能说 Bun 已让所有文件操作自动重试。当前验证只证明原语行为，**没有复现实际杀毒软件导致的某一业务链失败**。
- 旧 fork `packages/opencode/src/util/filesystem.ts:116` 的 `withRetry` 对全部异常重试（Windows 最多 50 次，每次 100ms），且属于旧 runtime；不向 v2 FileSystem 层盲目整体移植。将来若具体幂等业务入口复现，应在该入口针对暂态错误设计有界 retry，避免永久权限错误也延迟或部分写入重复执行。
- 本子任务不拥有 FSUtil 生产修改权；保留失败与恢复证据，把业务级瞬时锁恢复列为未覆盖项。

## 阶段 5 续轮：Windows MCP Job Object

### 已批准目标与实现前对照
- 用户明确要求：不能将真实复现的 detached MCP orphan 留作 skip；实现本地 Windows MCP 专属 containment，保留普通 shell、远程 Environment 和非 Windows 行为。
- 续轮开始时两个生产文件仍为官方基线；诊断已连续复现 2 fail，所有 fixture 完成有界 cleanup。前述基线记录和失败结果保留，不能用本轮通过覆盖原始证据。
- 真实运行环境：Bun `1.4.2 (744846f84)`、Node `v24.20.0`、系统 Windows PowerShell `5.1.26100.9444`，64 位。没有安装软件或 native package。

### 方案与职责边界
1. `McpStdio.make` 只将当前 StandardCommand 加入进程内 WeakSet（`McpWindows.own`）；**不替换 command/args/cwd/env，不给远程命令注入宿主环境或 PowerShell 路径**。
2. `Environment.environment.ts` 的隐式本地路径来自 `makeLocalDriver(spawner)`，workspace 路径由 `workspace.connect(...).driver.spawner` 提供。只在最终的本地 `CrossSpawnSpawner.launchProcess` 且 `process.platform === "win32"` 时消费这个 capability。
3. WeakSet 标记不属于可序列化 Command 字段；remote driver 得到原始命令，跨进程传输不会携带宿主 wrapper。若一个 driver 在本进程直接使用 CrossSpawnSpawner 实际运行 Windows 命令，则 containment 在这个实际本地执行点应用。
4. 普通 shell 不调用 `own`，spawn/kill/output deadline 逻辑不变。未修改 Environment、Location、workspace 接口，也未增加 schema/Protocol 字段。
5. 没有继续委派子智能体；独立测试/审查仍由父阶段 6/7 启动。

### 宿主生命周期与无竞态依据
- 使用系统绝对路径的 Windows PowerShell 5.1（`-NoProfile -NonInteractive`）运行小段内嵌 C# P/Invoke。无额外常驻服务、无 native 包、无生产脚本临时文件。
- 初始化顺序固定为：`CreateJobObjectW`（匿名、不可继承句柄）→ `SetInformationJobObject(JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE)` → `AssignProcessToJobObject(job, GetCurrentProcess())` → `CreateProcessW(target)`。
- **不是先启动目标再 assign**。目标从第一条指令起继承宿主 Job；只配置 `0x2000`，没有 `BREAKAWAY_OK` / `SILENT_BREAKAWAY_OK`。任何建立 Job 失败均在启动目标前返回错误，不降级为不受控运行。
- 宿主只等待目标进程 HANDLE，不等待 stdout/stderr EOF。目标退出后读取并保留其原退出码，宿主 `Environment.Exit(code)` 让 OS 关闭唯一 Job handle，杀掉所有仍存活的 Job 成员（包括 detached helper）。
- transport.close 仍沿用官方 stdin EOF grace 和后续终止；scope 取消仍走官方 acquireRelease。杀宿主会关闭 Job；不需要等遗留 helper 释放管道。
- 通用 spawner 的 `stop` 最终保持原样。仍使用现有的、针对本次 host PID 的 `taskkill /T` / 原生 kill fallback，这也覆盖宿主 Add-Type 编译初始化阶段；没有新增进程名扫描、CIM 轮询、事后推测子孙 PID 或进程名泛杀。
- Job 是生命周期约束，不宣称恶意 native 程序的安全沙箱；经外部既有服务/broker 发起的工作不是此 owned 进程树。

### 字节、argv、环境和兼容性
- 标准句柄用 `DuplicateHandle` + `STARTF_USESTDHANDLES` 直接传给目标。没有经过 PowerShell `Write-Output`、文本管道、编码转换或异步转发泵。
- 宿主 `$ProgressPreference=SilentlyContinue`，成功时不向 MCP stdout/stderr 写状态文字。错误仅写 stderr 并退出 127。
- 调试中真实发现把元数据命名为 PowerShell 自动变量 `$input` 会消耗 stdin：256 KiB 二进制回归当时得到 0 字节，已修正为独立元数据变量，并补充“目标 READY 后才发送及关闭 stdin”的测试，不仅验证启动前缓存数据。
- argv 使用锁定的 cross-spawn 7.0.6 解析器处理 PATH/PATHEXT/shebang/`.cmd`/`.bat` 及 cmd metachar；原生 exe 使用 CRT quoting。使用窄声明文件补齐其私有 parser 类型，core/util typecheck 均通过。
- argv、cwd 经唯一环境变量传递，**不拼进 PowerShell/C# 代码**；测试覆盖空参数、空格、中文/emoji、引号、末尾反斜杠、`& | ^ % !`、带空格/单引号/中文的路径和 `&` shim 文件名。
- PowerShell 会修改 `PSModulePath`，因此目标使用独立的原始 Unicode environment block，不继承宿主修改后的环境；保留 PATH、PATHEXT、cwd 及配置值。元数据按 16,000 字符分块，不把完整环境压进单个超长变量。目标中不存在内部 `OPENCODE_MCP_JOB_*` 元数据。
- `.cmd/.bat` 回归与同一生产 spawner 未包装时的实际输出对照，保持原 cross-spawn 的转义契约；不另行声称修复 cmd 本身固有的 `%` 等语义。

### 实质决策建议（供父流程同步 Auto 决策记录）
| 决策 | 比较 | 选择及理由 |
|---|---|---|
| placement 标记位置 | 修改 Environment public shape / 在 MCP 层直接包装 / 在本地执行点消费进程内 capability | 选最后者：无协议改动，远程原命令保持，local recording/decorator 仍可转交同一 Command |
| containment 实现 | CIM/PID 快照 / 大 native 包 / PS5.1 小型 Job 宿主 | 选 Job 宿主：目标创建前完成归属，detached 无法脱离，真实 API 实测可验证 |
| 标准流 | managed 文本或字节转发泵 / 原生句柄继承 | 选直接继承：避免重新实现 backpressure/EOF/编码及 pump 退出时序 |
| 环境 | 继承 PS 环境 / 明确 Unicode environment block | 选后者：避免 PSModulePath 等启动副作用污染真实 MCP 目标 |
| cmd argv | 自写 cmd 转义 / 复用锁定 cross-spawn parser | 选 parser：与现有 `.cmd/.bat` 启动语义一致，明确记录私有 API 升级风险 |
| 失败策略 | containment 失败后直接启动 / fail closed | 选 fail closed：不把失败伪装为已受控运行，不重新引入真实 orphan |
