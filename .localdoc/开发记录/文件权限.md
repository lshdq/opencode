## 前两轮设计取舍（历史，部分已被第三轮替代）
- **授权主体**：.NET 的 `WindowsIdentity.GetCurrent().User`，直接使用 SID 构造 ACE，不依赖 USERNAME、计算机名或账户名解析；PS5.1/PS7 相同。
- **创建即私有**：PS7 使用 `FileSystemAclExtensions.Create(CreateNew, ..., FileSecurity)`；PS5.1 使用 .NET Framework 的 `FileStream(path, CreateNew, FileSystemRights, FileShare, bufferSize, FileOptions, FileSecurity)` 构造重载。两者都将安全描述符传入原生文件创建，DACL 从创建开始即仅允许当前 SID，随后调用原写入入口写内容。不是写入凭据后再收紧。
- **完整 DACL 一次提交**：保护继承、移除其他显式 ACE，在内存完成后一次写回；保持当前用户的读写及 DELETE/WRITE_DAC/READ_CONTROL 权限。DELETE 是覆盖 rename 和 SQLite 删除 WAL/SHM 所需，避免旧实现 R/W 权限不能删除的问题。0400/0200 的数据权限分别保留只读/只写含义；owner 管理权限不向其他主体开放。
- **自检与恢复**：验证受保护 DACL、唯一当前 SID Allow ACE、无继承及精确 rights；再用真实 File.Open 检查请求的数据访问。脚本捕获失败时恢复原 DACL 并比较实际 SDDL，调用返回错误，不静默声称已加固。脚本正常执行 catch 时，新建失败文件被删除；外部 kill 的剩余空私有文件处理见下文。只变更已有文件的 Access 部分，不改 Owner/Group。
- **实测修正**：首次测试发现“对已有私有文件再次 SetOwner”需要 WRITE_OWNER，已改为仅写 DACL。恢复时必须通过 `SetSecurityDescriptorSddlForm` 将 Access 标记为待持久化；不能仅将未修改的 GetAccessControl 对象再传回并假设已经恢复。
- **子进程**：优先 `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`，系统宿主不存在时使用 PATH 中的绝对 `pwsh.exe` 候选，跳过相对路径。NoProfile/NonInteractive，最小环境；PSModulePath 只取宿主 `$PSHOME\Modules`，不继承污染值或应用 token。文件路径通过环境变量传递，中文、空格、单引号不拼接进脚本。不存在的已有文件先 lstat，不为其启动 PowerShell。
- **失败策略**：无法运行 PowerShell/应用 ACL 时，敏感写入或 DB 打开失败，保留/恢复已有权限，不采用无声的 insecure best-effort 写入。
- **FSUtil**：只有显式私有 mode 才触发；写入先以当前用户 RW ACL 完成，再应用其他 owner-only 数据权限。未传 mode、0644、非 Windows 的原 fs/chmod 路径保持原语义；不顺手 chmod 全部文件，也未覆盖 FileSystem 通用 chmod。
- **服务文件**：原临时文件路径和 rename 发布方式不变；已确认格式/频道归属的迁移源也收紧，避免留下公开的旧密码副本。迁移目标使用排他创建，重试不覆盖已有目标。不存在的 registration/config 不预先生成空注册文件。
- **SQLite**：仅本地 Bun/Node 驱动。新建主库带私有 DACL；已有 DB/WAL/SHM/journal 在打开前保护。执行原 WAL pragma 后，用无写入的 sqlite_master 查询使 WAL/SHM 实际创建，再在客户端、迁移和凭据写入开始前保护。保持原事务、bootstrap 锁、驱动关闭语义；`:memory:`、空 filename 和 workerd 不走该逻辑；非 Windows 不增加权限操作。

## 明确边界：不是所有 SQLite 侧文件的无条件保证
- 已实测覆盖：默认 WAL 模式新库、实际官方 schema 的 credential 写入、关闭删除侧文件、重新打开再创建、TRUNCATE checkpoint 后继续写入；Bun 与真实 Node 两套驱动均验证。
- **未覆盖**：运行中切换 journal_mode、`disableWAL`/DELETE 模式在事务中重新创建的 rollback journal，以及绕过本驱动的其他 SQLite 进程自行创建/替换侧文件。SQLite 的 Windows CreateFile 默认使用父目录 DACL，事后 chmod 无法消除已写凭据的暴露窗口，因此没有添加虚假的“每次写后修权限”补丁。
- 主库父目录及任意用户文件均不修改、不递归收紧；测试直接比较父目录和无关 sibling 的 SDDL。不提供对恶意共享父目录中其他用户删除/替换路径的完整完整性保证。
- **可行替代**：① 调用方明确配置一个专用且预先 owner-only 的 DB 目录，让所有未来侧文件安全继承；默认库迁移到此目录需另行设计 checkpoint、停机/锁、移动和回滚。② 实现 Windows SQLite VFS，在每次文件创建时提供安全描述符；跨 Bun/Node 驱动的原生集成明显超过本次最小补丁。未擅自实施任一父目录迁移。
- **已撤销首轮的 PS7 硬依赖**：正常 Windows 使用系统 PS5.1。清空 PATH 的真实测试仍完成新建、已存在 ACL 收紧、replace/read/write，证明不需要找到/安装 pwsh；另外显式运行 PS7 分支验证同一契约。两个受支持宿主都不可用时仍 fail closed。
- 每次实际收紧仍需启动 PowerShell，存在启动成本；没有宣称性能优化百分比，也没有用权限缓存跳过重开验证。

## 阶段 5 第二轮：执行上限、宿主兼容、正常 WAL 重建

### 有界执行与终止语义
- 每次生产 ACL 子进程固定 **10,000ms** 上限、`killSignal: SIGKILL`（Windows 终止进程）、64KiB 输出上限，并关闭 stdin。内部测试可缩短 timeout，不允许设置 0/无限/超过生产上限。
- 接通所有 service、FSUtil、Bun/Node driver 权限调用的 Effect AbortSignal。取消时同样终止宿主，不再让权限子进程在取消后无人管理地继续运行。
- executor 等待 **close** 后才完成 Promise，而非收到 abort error callback 就返回；确保自己的宿主及 stdio 已回收。ACL 脚本不创建任何后代进程。
- timeout/abort 不能依赖脚本 catch 执行。因此不在调用方执行 `/reset` 或启用继承：完整 DACL 从始至终是在内存构造，然后单次提交，进程被杀时磁盘上只会是原 DACL 或已经包含正确当前 SID 的完整私有 DACL，不存在先去掉授权再 grant 的空权限中间态。
- 被杀前刚创建的文件可能留下**空的私有文件**。调用报告失败，不写入后续秘密；不盲删路径或扩大权限，避免误删其他同用户并发调用已经接手的文件。owner 保留 DELETE/WRITE_DAC，可以正常重试、覆盖或清理。现有文件内容保留。
- Windows 迁移只忽略脚本明确报告的 **AlreadyExists**，不再通过宽泛 `Effect.ignore` 吞掉 private creation 的 timeout、取消或权限失败。普通非 Windows 分支保持官方行为。

### 可复核的真实失败测试
- 生产 ACL 脚本完成真实操作后，在**同一宿主**写测试 PID 标记并睡眠 60 秒；设置 4 秒 timeout。分别覆盖新建和已有文件，断言 8 秒内拒绝、PID 已不存在、DACL 仍仅当前 SID、旧内容/空内容正确，并能 read/write/rename/delete。没有 mock exec/helper。
- 另一用例等到真实 PID 标记后 AbortController.abort，断言 2 秒内返回错误、PID 已不存在、私有 ACL 不被 reset、owner 可继续写入。
- 预先 abort 的 FileMode.prepare 也实测拒绝，目标文件不存在。
- PS5.1 默认路径下，原有权限/失败恢复全部重新运行；PS7 显式分支额外验证创建、移除其他 ACE、原子替换、真实访问验证失败后恢复原 SDDL。

### 调用数量和启动延迟复核
- 不增加权限缓存，不因曾加固过就跳过重验；仍仅跳过确实不存在的已有文件。没有递归改父目录，也没有为优化改 SQL 事务。
- 默认新库或最后连接正常关闭后的 reopen：主库 1 次、打开前侧文件不存在 0 次、初始化后 WAL/SHM 各 1 次，合计 **3 个宿主进程**。保留的 WAL/SHM 在打开前及初始化后都验证，通常 **5 次**；存在 rollback journal 时还有明确的对应检查。
- 同机单次 `bun -e` 探针分别对同一宿主调用 production `FileModeWindows.execute(script, variables, {command})` 4 次（第 1 次创建，后 3 次重验），然后删除隔离目录。实测毫秒：**PS5.1 [515, 389, 395, 388]；PS7 [2968, 983, 785, 758]**。这是文件权限操作样本，不是完整应用冷/热启动基准，不能推导全应用加速百分比。
- 因此选择绝对系统 PS5.1 为默认，同时消除 PS7 安装依赖和本机较高的宿主启动成本；不引入缓存或常驻权限进程。单次调用仍有成本，多步权限操作的总上限是有限调用次数乘以单次上限，不声称整套服务启动严格 10 秒完成。

- Bun 的真实官方 credential schema 测试在 scope 关闭后断言 **WAL 和 SHM 都已消失**，再创建全新的数据库 layer，读取已提交凭据、再次写入，检查重新创建侧文件的 SID/DACL；不是复用第一次的私有文件。
- Node 24 的真实 `node:sqlite` 子进程同样明确断言最后连接 close 后两个侧文件 ENOENT；第二次打开验证 `after-checkpoint` 持久值并检查新 WAL/SHM DACL。

## 阶段7回修（第三轮，当前有效方案）

### 输入与决策
- 已完整读取 `.localdoc/审查记录/审查报告-v2权限与平台.md`，确认 R-01 阻塞、R-02/R-03 应改，不用“秘密尚未写入”解释掉已授予的读取句柄。
- Auto 批准的最小可靠方案是**目录创建时继承**，不是预创建侧文件后猜测 SQLite 不会替换，也不是 VFS 框架。无数据库文件/目录迁移，无事务、选举、MCP、spawner 或构建脚本改动。

### R-01：从初生起阻止读取句柄
1. `Database.Options.privateDirectory` 和底层 ClientConfig 是显式 ownership 授权。CLI 的 `databaseOptions(global.data)` 仅在 **OPENCODE_DB 未设置**时传 true，默认 DB 文件仍位于原来的 app data 路径；任何显式 override（相对、绝对、空字符串及 memory）都不自动授权改父目录。
2. 在创建/打开数据库之前，单个权限进程先读取目录 DACL。标准为：protected、唯一当前 SID Allow FullControl、ObjectInherit + ContainerInherit、无传播限制。已满足则不重复写目录 ACL。
3. 只有显式 app-owned 目录才可设置上述 ACL；其现有内容不移动、不截断。Windows 可能将继承规则传播至该应用目录中的继承型后代，这是明确授权的 app-owned 边界；代码不遍历目录树，更不会对任意 custom parent 递归 chmod。
4. **自定义目录只校验、不修改**。不满足标准时给出 actionable error，主库和侧文件尚未创建/修改。用户应先明确准备专用私有目录，或者使用默认位置；不能靠此补丁悄悄改共享目录、移动旧 DB 或丢弃旧数据。
5. 同一进程在目录确认安全后保护已有主库及已有 WAL/SHM/journal。随后才调用原 SQLite constructor/pragma。移除了“SELECT 物化侧文件 → 再 PS chmod”的后置流程；新 WAL/SHM 在 SQLite 的创建系统调用中继承唯一当前 SID，末连接关闭后重建也一样。
6. 安全依据是 Windows **创建时继承**，不是“轮询没赶上窗口”。默认继承规则在目录上先成立，因此没有由另一主体先取得 read handle、随后只收紧 DACL 的正常初生阶段。

#### 真实攻击性回归
- 新增 C# / Win32 测试 fixture：用 `CreateRestrictedToken` 的 Everyone restricting SID 做真实访问检查；**打开和读取均在 impersonation 下执行**，不是 mock ACL。无需创建系统账号或管理员操作。
- 正对照：给普通测试文件 Everyone Read，受限 token 成功取得读取句柄；随后真实 FileMode 收紧 DACL，再写 fixture secret，旧句柄仍成功读到新内容。该用例复现审查指出的 Windows 句柄性质，证明探针不是“永远打不开”。
- 负对照：先应用私有继承目录再创建文件，受限 token 从创建之前开始尝试打开，一直观察到写入后；`opened=0`、真实 ERROR_ACCESS_DENIED 次数大于0、不能读取 fixture secret。
- Bun：真实官方 credential schema 写入 JSON 凭据 fixture；Node：真实 `node:sqlite` driver 写入 credential fixture。两个 runtime 都在 observer 活跃期间完成首次创建、最后连接关闭后 WAL/SHM ENOENT、第二次创建、读写与实际继承 SID 检查。observer 在两轮结束之前不得提前退出。
- 自定义不安全目录：Bun 同时检查已有/不存在主库，Node 检查不存在主库；失败前后父目录/sibling/已有数据 SDDL 和内容保持不变，没有新库或侧文件。默认 app-owned 情况还检查更上级目录 SDDL 不变。
- PS5.1 为默认真实执行宿主；PS7 另有私有目录建立/重验/已有文件字节不变回归。
- 另有真实 junction 回归：app-owned 目录内的 junction 指向另一个目录，设置继承后外部目录、其数据文件及更上级目录的 SDDL/内容均不变。权限路径在进入最小环境子进程前用父进程 `path.resolve` 固定，覆盖相对路径与中文/引号目录，避免 PowerShell 当前目录语义差异。

### R-02：迁移不再发布空占位
- Windows 迁移在目标的同一父目录使用 `FileSystem.makeTempDirectoryScoped` 创建唯一目录。实读 rc.112 的 `NodeFileSystem.ts:183-190`，其实现为 `Effect.acquireRelease(mkdtemp, recursive remove)`；临时目录的所有权在权限创建前已明确。
- 目录内用真实 FileMode 原子私有创建 `content`，完整写入源文本后，调用 `fs.link(temp, target)` **原子且 no-overwrite 发布**。同卷 NTFS hard link 保留该 inode 的私有 DACL，目标永远不是未写完的占位文件。
- 只忽略 link 的 AlreadyExists（并发赢家），不吞写入/权限/其他发布失败。scope 只删自己 mkdtemp 所有的目录，不删正式目标、源文件或另一个迁移的文件。
- 正常异常和 Fiber 中断都在权限宿主回收后清理临时目录；整个进程被外部杀死可能留下独立私有临时目录，但不会留下空正式目标，下一次迁移采用新临时目录可正常重试。
- 配置和 registration 两入口均测试：prepare 完成后的真实 OS 写失败、写前中断、prepare 宿主仍活时中断、并发已完成赢家、两个真实迁移同时发布。检查原配置/密码保持、目标完整、重试成功、managed 失败后临时目录已清除。未放宽原 no-overwrite 断言。
- 非 Windows 保持原官方 wx/mode 分支。Windows 不支持同卷 hard link 的文件系统会明确失败，不降级为先公开目标再复制。

### R-03：Fiber.interrupt 等到真实 cleanup
- 新增小型复用 `FileModeEffect.run`：`Effect.callback` 创建自己的 AbortController，正常完成传递结果/错误；取消 finalizer 先 abort，再在不可中断的**清理阶段**等待同一个 pending Promise settle。不会把整个权限操作设为不可取消。
- executor 的 Promise 自身等待 child.close；两层结合才建立 “Fiber.interrupt 返回 → executor close 已完成” 的正确所有权边界。cleanup join 归并 pending 错误，仅为等候终止；正常安全失败仍进入 error channel。
- FSUtil、ServiceConfig/Registration、Bun/Node driver 全部接此 wrapper，不再用 tryPromise/promise 直接包装权限作业。UnknownError 带上可读 message，unsafe custom directory 的上层错误可操作。
- 实测真实 FSUtil 的 JSON/string/bytes、真实 ServiceConfig 密码、两个 migration 入口、真实 SQLite acquisition。故障注入只在 subprocess 边界：执行完整生产权限脚本后，让同一宿主写真实 PID marker 并睡眠；不替换 FileMode 算法。中断完成时断言 executor finally/close 已发生、PID 不存在、未继续写秘密、文件可立即清理/重试。

### R-04：固定阶段批处理，而非权限缓存
- 将目录检查/建立、主库、已存在的三个侧文件放进**一个** bounded PS 调用。新库、正常 reopen、retained WAL/SHM 都只有一次宿主启动；不需要 client 返回前的第二轮 chmod。
- 每次实际数据库 open 都重新读取目录和文件 ACL，无跨调用 cache，不因上次安全而跳过本次检查。单次仍为10秒、64KiB、SIGKILL/AbortSignal 与 close join。
- 同机权限阶段探针：`prepareDatabase(file, true, true)` 四次，首次新建后重验为 **[283,234,233,245]ms**；另持有真实 WAL 模式连接、让 WAL/SHM 存在后四次为 **[290,238,235,232]ms**。临时数据库和连接已关闭清理。仅为权限阶段样本，不是完整启动性能百分比。
