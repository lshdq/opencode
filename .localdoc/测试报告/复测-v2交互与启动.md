## 测试失败分析及实际修正

首个 B 组合唯一失败：`failed command discovery is visible, retryable and never replays the draft automatically`，源文件原第 140 行。实际收到 **kind=command, name=review, text=captured**，发生在点击 Retry 之前；不是 F-01 的普通 prompt 误分类。

原因及边界：
1. 原 fixture 用 `reads === 1` 返回 503，第二次 GET 即成功。启动有多处 Location sync 入口，失败资源不会被成功缓存；“屏幕曾显示资源失败”不能保证用户 Enter 时目录仍未加载。
2. 该 fixture 中 `review` 只可能来自第二次及后续成功 GET。因此收到正确 command 本身就说明 catalog 已有 review，不能拿它作为“目录仍不可用时发送”的生产反例。
3. 仅修测试：以显式 `recovering` 控制故障，恢复前所有 GET 返回 503；点击真实 Retry 前打开恢复开关，后续响应仍由 gate 持有；比较点击前后 GET 计数增长，再放开响应。
4. 保留原所有业务断言；增加 Retry HTTP 在途期间无发送、草稿不变两项断言，并等待 **Commands unavailable** 可见。目录恢复后仍无自动发送，最后明确 Enter 才发 command。
5. 没有增加 timeout、skip、删除用例、放宽发送预期或改生产代码。最终测试数量仍是 9 项，断言从 14 增为 16。

这是测试场景控制修正，不把最初失败归为已确认的生产缺陷，也不隐去失败过程。
