## 决策列表

### DEC-001: references 解耦采用共享纯函数方案
- 阶段：方案设计（阶段 2，已获用户批准）
- 背景：`agent.ts` Agent.state 为获取 reference 目录白名单，经 `locations.get(ref)` 编译整套 30 服务 location bundle（实测 3.7s git 风暴），是启动最大瓶颈。
- 可选方案：A) 提取共享纯函数（config 文档→Source→绝对路径），插件与 agent 共用，agent 不再编译 bundle；B) 为 Reference/PluginV2 提供轻量独立 node，agent 编译小子图；C) 保持编译但整体后台化（延迟首 prompt）。
- 最终选择：方案 A。
- 选择理由：`config-reference` 是 Reference 唯一生产者且纯从 config 推导（git 物化本就 fork 后台），纯函数可完全复用现有推导逻辑（单一事实来源），行为等价、改动面最小、最符合上游规范；B 需拆分层图风险更大；C 保留无用编译。
- 影响：agent 权限白名单生成时机不变、结果等价；location bundle 从启动关键路径移除；前提"唯一生产者"在 T0 验证，不成立则退回方案 B。

### DEC-002: 预热触发点放在 Agent.state 完成后 fork
- 阶段：方案设计（阶段 2，已获用户批准）
- 背景：bundle 移出关键路径后，若完全惰性，首个 prompt 需现场编译 3-4s，体感退化。
- 可选方案：A) Agent.state 计算完纯函数白名单后立即 `Effect.forkIn` 预热主 location（worker 线程执行，与 TUI 主线程渲染并行）；B) 服务端 bootstrap.run 尾部统一预热；C) TUI ready 后发专用 RPC 触发预热。
- 最终选择：方案 A。
- 选择理由：改动局部（同文件移除处补预热）、无新 RPC/新依赖、预热始于 agents RPC 返回时点（sync 阻塞阶段末尾），与"ready 后预热"意图一致；worker 线程执行避免与渲染争用主线程。
- 影响：预热失败仅记日志不影响主流程；需验证 LayerMap 同 key 并发去重，防止预热与首次 prompt 双编译。

### DEC-006: V2 配置文档发现逻辑提取为共享纯函数供 agent 使用
- 阶段：阶段 5（T4 设计细化）
- 背景：V2 `Config.Service` 是 location-scoped（core/config.ts:223 `makeLocationNode`，依赖 Location.Service + Policy），agent（instance-scoped）无法在不编译 location bundle 的情况下取 `entries()`；而 reference 相对路径解析需要逐文档目录信息，V1 合并配置已丢失该信息。
- 可选方案：A) 提取 core/config.ts 的文档发现+解析（fs.up、loadFile、排序）为共享函数，V2 层与 agent 共用，agent 用 ctx.directory/project 直调；B) agent 单独读 V1 references 并猜测路径基；C) 给 V2 Config 做独立轻量 node。
- 最终选择：方案 A。
- 选择理由：单一事实来源（发现/解析/排序/V1 迁移逻辑只有一份）；多读几次小 json 文件成本 ~10-40ms，远低于 bundle 编译 3.7s；方案 B 无法正确解析相对路径，C 需拆 Location/Policy 依赖链风险大。
- 影响：core/src/config.ts 重构出 `discoverDocuments` 类导出（保持层行为不变）；agent 启动多一次轻量文件发现。

### DEC-007: 双编译真正根因为 Ref 键不等价，采用生产者侧条件展开修复
- 阶段：阶段 5（性能实测发现 DEC-005 修复后仍双编译，诊断定位）
- 背景：诊断日志证实只有一套 LocationServiceMap（DEC-005 已生效），但同一 directory 的 "booting location services" 仍出现两次。bun 实证：`Location.Ref.make({directory, workspaceID: undefined})` 与 `Location.Ref.make({directory})` 的 `Equal.equals` 为 false、Hash 不同（属性显式 undefined vs 缺失）→ LayerMap 两个条目各编译一次。产生显式 undefined 的三处：server/src/location.ts ref()、server/src/middleware/session-location.ts、core/src/session/info.ts。
- 可选方案：A) 三个生产者改为条件展开（`...(x ? {workspaceID: X} : {})`），属性缺失时不含字段；B) 在 schema 层自定义 make 统一剥离 undefined 字段。
- 最终选择：方案 A。
- 选择理由：与仓库既有条件展开风格一致（reference.ts 同模式）；改动面最小、语义清晰；schema 层 make 为 effect Schema 生成物，包装改造影响所有调用方且偏离上游。
- 影响：HTTP 请求路径与 agent/system 路径的 Ref 归一为同一 key，bundle 只编译一次；此问题同时解释了优化前基线的双编译（DEC-005 只是其一部分）。临时诊断代码已全部撤除（git checkout 恢复）。

### DEC-003: git discover 合并保持逐项失败语义
- 阶段：方案设计（阶段 2，已获用户批准）
- 背景：三次 `rev-parse` 串行 spawn 在 Windows 每次约 50-100ms。
- 可选方案：A) 合并为单次 `git rev-parse --show-toplevel --git-dir --git-common-dir`，按行解析并保持"gitDir/commonDir 失败→undefined、topLevel 失败→回退 cwd"语义；B) 仅并行化三次调用；C) 不改。
- 最终选择：方案 A，输出解析在 worktree/bare/非 git 三场景实测验证；若单次调用在 bare 场景整命令失败导致语义无法保持，则该场景回退拆分调用（记录实测结论）。
- 选择理由：单次调用收益最大且 git rev-parse 支持多参数输出多行；语义保持通过解析层实现。
- 影响：discover 调用方（Project.resolve、watcher、snapshot）全部受益，无需各自改动。

### DEC-004: 纯 config 推导与现状行为等价（T0 前提验证结论）
- 阶段：阶段 5 前置审计（T0）
- 背景：T0 验证发现外部插件可经 `ctx.reference.transform` 增删 reference（DEC-001 的"唯一生产者"前提字面上不成立）。
- 可选方案：A) 仍用纯推导；B) 退回 DEC-001 备选（Reference 轻量 node）。
- 最终选择：方案 A，但推导必须基于 V2 `Config.Service.entries()`（与插件逐字对齐），复刻 validAlias/local()/localPath()/parse+isRemote+validateBranch 全部校验。
- 选择理由：Agent.state 的权限白名单是**构建时快照**；外部插件经 config-plugin fork 加载在 Agent.state 之后注册 transform，现状白名单本就不含插件新增条目（竞态遗漏）。纯推导结果与现状快照等价；插件条目在两种实现中同样不在白名单内，无行为回退。
- 影响：无需拆层图，改动面更小；实现时严格复用 config/plugin/reference.ts 的推导逻辑（提取共享函数）。

### DEC-005: 双套 location 编译由 LayerMap 实例分裂导致，纳入 T4 统一
- 阶段：阶段 5 前置审计（T0）
- 背景：实测两次 "booting location services"（同 directory+workspaceID）根因是两套 LayerMap 实例：`httpapi/server.ts:274` 每次调用 `buildLocationServiceMap()` 自建，而 `agent.ts:441` 等使用 `location-services.ts:115` 导出的单例 `locationServiceMapLayer`——同一 location 被两套缓存各编译一次（双倍 git 风暴/内存）。
- 可选方案：A) `createRoutes` 改用共享单例层；B) 保持两套但互相预热；C) 不处理。
- 最终选择：方案 A，由 T4 子任务核实 server 测试场景是否依赖独立实例（若依赖则改为可注入、默认单例）。
- 选择理由：单实例天然去重（Effect LayerMap 同 key 共享构建），消除双编译；预热策略（DEC-002）也只需预热一套。
- 影响：packages/opencode/src/server/routes/instance/httpapi/server.ts 纳入 T4 变更范围；需跑 server 相关测试确认无跨实例状态污染。
