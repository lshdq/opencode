# 决策记录：dev-workflow 执行模式优化

## 决策列表

### DEC-001: 非 Auto 模式命名
- 阶段：方案设计
- 背景：需要避免含义模糊的“当前模式”。
- 可选方案：交互模式、标准模式、交互决策模式。
- 最终选择：交互决策模式。
- 选择理由：名称直接体现该模式在决策点暂停并询问用户的核心差异。
- 影响：阶段 2 选项、模式处理和强制规则统一使用该名称。

### DEC-002: 阶段 2 确认与 plan_exit 协作方式
- 阶段：方案设计
- 背景：用户要求方案确认与模式选择合并，但 plan_exit 的内置提问固定为 Yes/No，不能表达三种结果。
- 可选方案：修改 OpenCode 源码、方案确认后再询问模式、先三选一再用 plan_exit 执行技术切换。
- 最终选择：先用 question 完成三选一；获批后再调用 plan_exit，后者仅承担 agent 切换。
- 选择理由：无需修改 OpenCode 源码，同时保持用户对方案和模式的一次业务决策。
- 影响：plan agent 下仍可能出现 plan_exit 固有的 Yes 点击，但该点击不再承担执行模式选择。

### DEC-003: 决策记录创建时机
- 阶段：生成文档
- 背景：同一工作流的所有 Auto 决策需要写入同一文件。
- 可选方案：首次出现决策时创建、阶段 3 统一创建、每个决策单独创建文件。
- 最终选择：阶段 3 生成一次时间戳并创建文件，后续持续追加。
- 选择理由：文件路径从开发开始即稳定，避免多文件分散和首次决策时遗漏记录。
- 影响：即使后续没有新增自主决策，也会保留执行模式和初始化信息。

### DEC-004: Agent 切换判定标准
- 阶段：执行开发
- 背景：OpenCode 支持名称不是 build 但具备完整开发能力的自定义 agent。
- 可选方案：只按 agent 名称判断、按完成任务所需的工具能力判断。
- 最终选择：按编辑、命令、子智能体和验证能力判断是否需要切换。
- 选择理由：避免对具备能力的自定义 agent 产生虚假硬阻塞。
- 影响：仅在当前 agent 确实缺少必要能力且无法切换时要求用户介入。

### DEC-005: 交互决策模式的文档审核
- 阶段：执行开发
- 背景：全局 AGENTS.md 原有流程包含需求文档和测试用例的用户审核，而 Auto 模式要求阶段 3 后不中断。
- 可选方案：删除所有文档审核、两种模式都审核、仅交互决策模式审核。
- 最终选择：Auto 模式直接继续，交互决策模式保留阶段 3 文档审核。
- 选择理由：同时满足 Auto 连续执行和非 Auto 模式保持原有交互行为。
- 影响：全局 AGENTS.md 改为将阶段 3 审核方式委托给 dev-workflow 的模式规则。

### DEC-006: 时间戳冲突处理
- 阶段：执行开发
- 背景：`yyyyMMddHHmmss` 精确到秒，同一功能并发工作流可能生成相同路径。
- 可选方案：改用毫秒、覆盖已有文件、逐秒递增至可用路径。
- 最终选择：保留用户确认的秒级格式，冲突时逐秒递增至首个可用路径。
- 选择理由：不改变统一时间戳格式，同时避免覆盖或混写记录。
- 影响：创建决策记录前必须检查目标路径是否存在。

### DEC-007: 实质决策记录口径
- 阶段：执行开发
- 背景：自主决策、阶段 2 已批准方案和普通实现细节之间需要统一可判定边界。
- 可选方案：只记录方案外决策、记录所有操作、记录 Auto 生命周期内所有 AI 实质决策。
- 最终选择：记录 Auto 生命周期内所有 AI 实质决策，并在阶段 3 补录已批准方案中的 AI 实质决策。
- 选择理由：符合“所有决策项”要求，同时通过实质影响标准避免记录膨胀。
- 影响：排除用户选择、唯一修复路径、强制动作和普通编码细节。

### DEC-008: 局部验证阻塞处理
- 阶段：独立测试
- 背景：外部测试环境不可用不应阻止仍可执行的测试和代码审查。
- 可选方案：立即停止工作流、忽略未执行测试、先完成可执行工作再汇报验收阻塞。
- 最终选择：先完成所有不依赖该环境的测试、审查和修复，最后汇报未验证项。
- 选择理由：最大化 Auto 模式可完成的工作，同时不把未验证内容误报为通过。
- 影响：测试报告必须明确未执行项及原因。

### DEC-009: 三选一的非标准回答处理
- 阶段：执行开发
- 背景：部分 question 工具无法关闭自定义答案，用户也可能取消或不作答。
- 可选方案：猜测用户意图、默认 Auto、统一视为未批准。
- 最终选择：自定义答案、取消和空回答统一视为未批准并停留在阶段 2。
- 选择理由：方案和执行模式必须得到明确授权，不能推断或默认。
- 影响：工具支持时使用 `custom: false`，不支持时仍有安全降级路径。

### DEC-010: 基本验证失败后的阶段可达性
- 阶段：执行开发
- 背景：基本验证最终失败时仍需完成不依赖该失败项的测试和代码审查。
- 可选方案：只有验证通过才进入阶段 6、验证执行完毕即可进入阶段 6。
- 最终选择：阶段 6 入口改为基本验证已执行，并按结果决定完整测试或仅执行仍可行的测试。
- 选择理由：消除阶段入口与局部阻塞继续规则的矛盾。
- 影响：验证失败不会提前终止仍有价值的测试和审查。

### DEC-011: 测试失败规则的源头一致性
- 阶段：独立测试
- 背景：dev-workflow 的子智能体 prompt 与 test-workflow 原有失败询问规则冲突。
- 可选方案：只在 prompt 中覆盖、同步修改 test-workflow 的被调用分支。
- 最终选择：同步修改 test-workflow，区分用户直接调用和父流程子智能体调用。
- 选择理由：从规则源头消除冲突，不依赖模型自行判断指令优先级。
- 影响：独立测试子智能体无论是否具备 question 能力，都直接完成报告并返回父流程。

### DEC-012: Auto 提醒触发点
- 阶段：执行开发
- 背景：具备完整能力的自定义 agent 不发生 build 切换，但仍需要 Auto 权限提醒。
- 可选方案：进入 build 时提醒、用户选择 Auto 后立即提醒。
- 最终选择：用户选择 Auto 后立即提醒，不绑定 agent 名称或切换动作。
- 选择理由：覆盖所有可执行 agent 路径，避免权限确认打断 Auto 流程。
- 影响：提醒发生得更早，且无需等待用户回复。

### DEC-013: plan_exit 拒绝后的批准有效性
- 阶段：执行开发
- 背景：plan_exit 拒绝可能只是暂缓切换，也可能随后修改方案。
- 可选方案：一律重新确认、一律保留批准、仅方案实质修改时使批准失效。
- 最终选择：方案未修改时保留批准，实质修改时重新三选一确认。
- 选择理由：避免无意义的重复确认，同时保证修改后的方案获得明确批准。
- 影响：工作流需跟踪 plan_exit 拒绝后方案是否发生实质变化。

### DEC-014: 决策文件并发创建
- 阶段：生成文档
- 背景：先检查后创建存在两个并发工作流同时选中相同路径的竞态。
- 可选方案：普通检查后创建、毫秒时间戳、排他创建并在冲突后递增重试。
- 最终选择：使用仅当不存在时创建的原子或排他语义，冲突后逐秒递增并重试。
- 选择理由：保留用户指定的秒级时间戳格式，并可靠避免覆盖或混写。
- 影响：不能把预检查结果当作创建成功，必须处理创建时冲突。

### DEC-015: 独立测试智能体的修改边界
- 阶段：独立测试
- 背景：禁止测试智能体修改“源代码”会同时禁止 test-workflow 要求持久化的测试代码。
- 可选方案：完全禁止修改、允许修改所有代码、只允许修改测试代码。
- 最终选择：禁止修改生产代码，允许并要求在覆盖不足时补充或修改可持久化测试代码。
- 选择理由：既保持测试智能体不修生产缺陷的职责边界，又保证测试覆盖和后续回归能力。
- 影响：生产代码缺陷仍由主智能体修复，测试智能体可维护项目测试目录中的代码。

### DEC-016: 测试场景枚举统一
- 阶段：独立测试
- 背景：dev-workflow 和 test-workflow 对“通用”与“文档验证”的枚举声明不完整。
- 可选方案：各 skill 保留自己的子集、统一为四种完整场景。
- 最终选择：统一使用“框架代码 / 业务代码 / 通用 / 文档验证”。
- 选择理由：实际流程已支持四种场景，统一声明可避免合法输入被误判或文档遗漏分类。
- 影响：测试用例模板、子智能体参数和 test-workflow 输入说明保持一致。

### DEC-017: 文档验证场景路由
- 阶段：独立测试
- 背景：文档验证不需要单元测试或集成测试，但原流程在场景分流前无条件执行单元测试阶段。
- 可选方案：沿用完整测试流程、在流程入口按场景分流。
- 最终选择：文档验证直接执行只读文档检查并输出报告，跳过代码测试阶段。
- 选择理由：避免无关项目测试和错误补测，同时让 test-workflow 明确支持文档验证。
- 影响：test-workflow 描述和流程增加文档验证分支。

### DEC-018: 测试子智能体的用户交互边界
- 阶段：独立测试
- 背景：业务测试的部署确认可能让子智能体直接询问用户并打断父流程。
- 可选方案：子智能体直接询问、由子智能体记录并返回父流程。
- 最终选择：父流程调用时，部署和环境问题只记录并返回，由主智能体按执行模式处理。
- 选择理由：用户交互应由掌握完整工作流状态和执行模式的主智能体统一负责。
- 影响：子智能体 prompt 增加执行模式，test-workflow 增加父流程调用分支。

### DEC-019: 测试代码变更审查闭环
- 阶段：代码审查
- 背景：独立测试可修改当前项目或外部仓库的测试代码，原审查范围可能遗漏这些变更。
- 可选方案：只审查生产变更、报告并审查全部测试代码变更。
- 最终选择：测试报告列出全部测试文件和所属仓库，阶段 7 全部纳入审查。
- 选择理由：测试代码同样可能包含错误或副作用，必须进入质量闭环。
- 影响：外部仓库测试变更必要时按仓库单独启动独立审查。

### DEC-020: 阶段 3 实质反馈处理
- 阶段：生成文档
- 背景：交互决策模式的文档反馈可能改变已经批准的方案。
- 可选方案：任何反馈都只更新文档、实质反馈使批准失效并回退流程。
- 最终选择：非实质文字修订留在阶段 3；实质反馈返回阶段 1 或阶段 2并重新三选一确认。
- 选择理由：避免未经批准的范围或架构变化直接进入开发。
- 影响：阶段 3 审核需判断反馈是否改变已批准方案的实质内容。

### DEC-021: 审查修复后的质量收敛
- 阶段：代码审查
- 背景：审查修复会改变生产代码或测试代码，修复前的测试结果不能证明最终版本正确。
- 可选方案：修复后只复审、修复后重新验证和测试再复审。
- 最终选择：每轮修复后重新执行受影响的基本验证、独立测试和独立审查。
- 选择理由：保证最终测试和审查针对同一版变更，并形成可收敛的质量闭环。
- 影响：阶段 5-7 重复执行，直到测试和审查同时通过或确认硬阻塞。

### DEC-022: 修复动作与修复方案分离
- 阶段：执行开发
- 背景：测试和审查问题必须修复，但具体修复方式可能构成新的实质决策。
- 可选方案：所有修复都自主执行、所有修复都询问、只对修复方案的实质决策按模式处理。
- 最终选择：不询问是否修复；具体方案构成实质决策时按 Auto 或交互决策模式处理。
- 选择理由：既不中断必要修复，又保留交互决策模式对重大方案选择的控制。
- 影响：测试和审查结果处理必须复用统一的实质决策定义。

### DEC-023: 业务部署测试闭环
- 阶段：独立测试
- 背景：部署前置由父流程处理时需要遵守执行模式，并确保部署后补做未完成接口测试。
- 可选方案：统一自主部署、统一询问、按模式处理后重新测试。
- 最终选择：限定已批准的非生产环境，部署决策按模式处理，部署完成后重新启动独立测试。
- 选择理由：避免交互模式越权和生产环境风险，同时保证接口用例最终执行。
- 影响：无权限或环境时先完成其他工作，最后将未验证项作为验收硬阻塞。

### DEC-024: 审查上下文完整性
- 阶段：代码审查
- 背景：审查测试代码需要知道测试用例目标和最近测试结果。
- 可选方案：只传需求文档、同时传测试用例和测试报告。
- 最终选择：审查 prompt 同时包含需求文档、测试用例和最近测试报告或完整摘要。
- 选择理由：让独立审查能够判断测试变更是否覆盖验收场景并识别遗漏。
- 影响：文档验证报告增加独立结果区，审查输入增加测试上下文。

### DEC-025: Auto 批准失效边界
- 阶段：执行开发
- 背景：plan_exit 拒绝后的方案修改需要重新确认，但阶段 3 后的 Auto 实质决策不应使批准失效。
- 可选方案：所有实质修改都重新确认、只限定在 plan_exit No 后且尚未开发的窗口。
- 最终选择：仅在 plan_exit No 后、进入阶段 3 前的实质方案修改使批准失效。
- 选择理由：既保护修改后方案的授权，又不破坏 Auto 模式后续自主决策。
- 影响：阶段 3 后严格按已选模式处理新决策。

### DEC-026: 父流程补测递归例外
- 阶段：独立测试
- 背景：全局规则要求代码修改启动 dev-workflow，但阶段 6 子智能体本就处于父 dev-workflow 中。
- 可选方案：补测递归启动新流程、把补测定义为父流程内部步骤。
- 最终选择：阶段 6 测试代码修改不递归启动 dev-workflow，生产代码仍交父流程主智能体。
- 选择理由：避免无限递归和无法完成的嵌套确认，同时保持生产修改受完整流程控制。
- 影响：全局 AGENTS.md 增加父流程内补测例外。

### DEC-027: 业务修复版本识别
- 阶段：独立测试
- 背景：生产代码修复后若不重新部署和确认版本，接口测试可能仍针对旧制品。
- 可选方案：复用已有部署、重新部署并校验可验证制品标识。
- 最终选择：影响部署组件的每轮修复都重新构建、部署、校验版本与就绪后复测。
- 选择理由：确保接口结果确实对应当前修复版本。
- 影响：测试输入和报告增加环境、预期制品、实际制品及就绪状态。

### DEC-028: 审查上下文扩展
- 阶段：代码审查
- 背景：需求和测试报告不足以验证实现是否符合批准方案、后续决策和基本验证状态。
- 可选方案：保持精简上下文、传递完整设计和验证上下文。
- 最终选择：增加批准方案、决策、基本验证结果和累计审查范围。
- 选择理由：使独立审查能识别偏离设计、未解决验证失败和范围遗漏。
- 影响：阶段 7 prompt 必须携带这些信息。

### DEC-029: 脏工作区与累计变更隔离
- 阶段：任务分解
- 背景：单纯 `git diff <base>` 会混入任务前改动，最近一轮测试报告又可能遗漏早期或外部变更。
- 可选方案：只用提交基线、记录初始状态并维护累计精确范围。
- 最终选择：开发前持久化各仓库基线，对既有修改保存快照或精确 diff，并跨轮次累计本流程变更。
- 选择理由：避免修改或审查用户既有工作，同时保证所有生产、测试、外部和忽略文件变更进入审查。
- 影响：新增审查范围文档并在阶段 7 作为权威范围输入。
