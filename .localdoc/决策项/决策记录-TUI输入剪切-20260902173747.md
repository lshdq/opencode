## 决策列表

### DEC-001: 在选区拦截器中实现剪切
- 阶段：方案设计
- 背景：`Ctrl+X` 同时是默认 leader，需要保证有选区时剪切、无选区时继续 leader。
- 可选方案：注册 `prompt.cut` 普通 keymap 命令；在现有高优先级选区键盘拦截器中处理 `Ctrl+X`。
- 最终选择：在选区键盘拦截器中处理 `Ctrl+X`，并抽取可独立测试的剪切函数。
- 选择理由：现有 `Ctrl+C` 复制已经使用同一机制；拦截器可以同步判断是否存在可删除选区，避免与 leader 的精确键和前缀序列产生歧义，也无需侵入 Prompt 命令注册。
- 影响：标准 TUI 中所有具备删除选区能力的聚焦编辑器可使用固定 `Ctrl+X` 剪切；不新增可配置的 `input_cut` 键位。

### DEC-002: 剪贴板异步写入与选区删除顺序
- 阶段：方案设计
- 背景：ClipboardService.write 是异步 API，等待写入后再删除可能因用户继续编辑而删除错误选区，立即删除则在底层写入失败时需要依赖 undo 恢复。
- 可选方案：等待写入完成后按原范围删除；捕获文本并立即删除，同时异步报告写入结果。
- 最终选择：捕获并提交剪贴板写入后立即调用编辑器删除选区。
- 选择理由：符合剪切的即时交互语义，避免异步期间选区和内容变化造成误删；删除操作由 OpenTUI 记录到撤销历史。
- 影响：底层剪贴板实际写入失败时文本已从输入框删除，用户可通过 undo 恢复；本次不扩大范围重构现有剪贴板错误传播机制。

### DEC-003: 禁用状态由编辑器目标动态暴露
- 阶段：代码审查修复
- 背景：全局高优先级剪切拦截先于 Prompt 的 onKeyDown 禁用保护执行，需要让通用选区工具识别当前目标是否允许剪切。
- 可选方案：将剪切逻辑移回 Prompt 专用 keymap；在 Prompt textarea 上暴露动态可剪切能力，由通用剪切函数检查。
- 最终选择：通过 textarea 的 `canCut()` 动态能力暴露 `!props.disabled`。
- 选择理由：保留已验证的 leader 同键拦截和通用编辑器剪切机制，同时以最小接口表达 Prompt 的动态禁用状态。
- 影响：内置 Prompt disabled 时不会剪切；其他未声明 `canCut()` 的普通可编辑 textarea 维持可剪切行为。

### DEC-004: 通过 TuiInput 注入测试剪贴板
- 阶段：代码审查修复
- 背景：真实 App 测试需要验证剪贴板零写入及恢复后的写入，同时不能访问开发机或 CI 的系统剪贴板。
- 可选方案：使用 Bun 模块 mock 替换剪贴板模块；将 ClipboardProvider 已支持的服务注入能力透传到内部 TuiInput。
- 最终选择：为 TuiInput 增加可选 ClipboardService，并传给 ClipboardProvider。
- 选择理由：显式依赖注入不依赖模块缓存和测试执行顺序，复用现有 Provider 接口，生产调用方省略时行为完全不变。
- 影响：TUI run 内部输入新增可选测试/嵌入能力；默认仍使用现有系统剪贴板实现。
