## 决策列表

### DEC-001: rg.exe 并发保护的锁选型
- 阶段：方案设计（阶段 2，补录）
- 背景：`packages/core/src/ripgrep/binary.ts` 的 check-then-download 无并发保护，多用户首次并发启动会在共享 `bin/` 上竞态（Windows 下 target 被执行时 copyFile 可能 EPERM）。
- 可选方案：① Flock（`packages/util/src/flock.ts`，锁根 `state/locks`，与 repos/npm/config 一致）；② 目标文件加版本化命名 + 原子 rename；③ 不处理，靠首装预热。
- 最终选择：① Flock。
- 选择理由：与代码库既有跨进程互斥机制一致，天然跨用户（锁在共享 state）；实现最小，不改变 `bin/rg` 的固定路径契约。
- 影响：首次并发下载被串行化；后到者在锁释放后复用已下载文件。

### DEC-002: service-config temp 唯一化实现
- 阶段：方案设计（阶段 2，补录）
- 背景：`service-config.ts` 的 `write` 使用固定 `<file>.tmp`，多用户同时 `service set` 会互相覆盖 temp。
- 可选方案：① 随机后缀（randomUUID/randomBytes）；② 复用 `service-registration.ts` 的 `.<id>.tmp` 模式；③ makeTempDirectoryScoped。
- 最终选择：① 随机后缀。
- 选择理由：`write` 无实例 id 可用；随机后缀最小且与库内既有临时文件惯例（`opencode-pty.<pid>.<uuid>.tmp`）一致；写入仍以 rename 原子发布。
- 影响：并发写不再互相覆盖 temp；最终内容为某一次完整写入（last-writer-wins，与现状语义一致）。

### DEC-003: file-mode 模块族的处置
- 阶段：方案设计（阶段 2，补录）
- 背景：彻底删除加固后，`file-mode.ts` / `file-mode-windows.ts` / `file-mode-effect.ts` 是否保留。
- 可选方案：① 三个模块全删（含测试 fixture 依赖一并清理）；② 保留 `command()/execute()` 供测试 fixture 读取 ACL。
- 最终选择：① 全删；测试 fixture（`file-acl.ts` 等）随之删除或内联 PowerShell 命令。
- 选择理由：运行时无任何调用方后保留即死代码；fixture 仅被本次删除的测试使用，`service-smoke.test.ts` 个别引用改为内联 powershell.exe 路径解析。
- 影响：测试面缩小；后续如需 ACL 工具需重新引入。

### DEC-004: fs-util 私有模式分支的收敛方式
- 阶段：方案设计（阶段 2，补录）
- 背景：`writeJson/writeWithDirs` 中 Windows FileMode.prepare/apply 分支删除后的落点。
- 可选方案：① 收敛为 `if (mode) yield* fs.chmod(path, mode)`（Windows 上 Node chmod 仅影响只读位，等效无操作）；② 完全删除 mode 参数。
- 最终选择：① 收敛 chmod。
- 选择理由：保留 Unix 语义与调用方签名兼容；Windows 上 chmod 对 ACL 无实质影响，符合"继承父目录"目标。
- 影响：调用方无需改动；Unix 行为不变。

### DEC-005: 共享 DB 多进程并发首次初始化的修复方式
- 阶段：阶段 6（独立测试发现 P0 缺陷后的修复决策）
- 背景：TC-003 稳定复现：`migration.ts` 的 `apply()` 在事务外读 `sqlite_master` 判空库，两进程并发首次初始化共享 DB 时均进 bootstrap 事务，后到者 `CREATE TABLE already exists` 后启动失败且无重试；`database.ts` 的 bootstrap 锁为进程内 Semaphore，不跨进程。原方案文档"后到者失败重试可恢复"的假设被测试证伪。
- 可选方案：① bootstrap/每条迁移失败后捕获错误并重查 `migration` 表/session 表，发现他人已完成则降级走 `applyOnly`/跳过该条，配一次有界重试（覆盖 SQLITE_BUSY）；② 引入跨进程文件锁（Flock on DB path）串行化全部迁移；③ 不修，部署侧保证单进程首启。
- 最终选择：① 捕获 + 重查降级 + 有界重试。
- 选择理由：不引入新锁层（与已批准方案"不引入额外锁层"一致）；正确性依赖 SQLite 事务原子性（后到者事务回滚无副作用），重查即可收敛；② 锁层侵入 DB 引导路径、耦合 Flock 与 core database 层；③ 违背多用户并发启动的核心验收标准（TC-003/验收 4）。
- 影响：并发首启后到者不再启动失败；串行场景行为不变；新增回归测试 `sqlite-shared-concurrent-start.test.ts` 必须通过。
